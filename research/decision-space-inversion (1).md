# Decision-Space Inversion: *Consistency Models for Semantic Memory in Stateless LLM Agents*

**Paper:** Dwayne McCoy, *Consistency Models for Semantic Memory in Stateless LLM Agents*  
**Target setting:** Kivi, as specified in *The Things Kivi Comes to Know*  
**Method note:** The paper is a qualitative literature synthesis, not a report of an implemented system or controlled experiment (paper §3, p. 3). Accordingly, “paper answer” below sometimes means a design position advocated by the paper, not a measured implementation choice. Where the paper supplies only an example, checklist item, or possibility, the entry says so. Where it supplies no answer, the entry says **underspecified**.

## 1. Decision Inventory

### A. Scope, workload, and system boundary

A stale or missed negative update can make a correction appear ineffective, a higher trust cost than stale background knowledge. (Kivi §§8–9.) |

## 3. Unexamined Defaults

These choices are either made implicitly or inherited from the literature without being framed as decisions.

| ID | Unexamined default | Evidence in the paper | Alternative this line of work rarely foregrounds |
|---|---|---|---|
| U1 | **Persistence is presumptively beneficial.** The paper asks how to keep semantic memory coherent, not whether a candidate should become memory. | §1, p. 1 defines semantic memory by persistence and continuity. | Treat non-retention as the default and require a positive, inspectable admission rule for every durable belief. |
| U2 | **Database replica consistency is the right abstraction for semantic consistency.** | §2, p. 3 says distributed-store principles apply to semantic stores. | Separate at least three guarantees: replica visibility, semantic conflict resolution, and epistemic/disclosure correctness; allow each to have different mechanisms. |
| U3 | **“Latest write” is meaningful and preferable.** | Strong consistency is described as returning the most recent write (§4.1, p. 4). | Preserve concurrent, source-qualified claims when no write has automatic authority; resolve based on subject, provenance, validity interval, or explicit confirmation. |
| U4 | **Every update is a positive value change.** | Examples concern task-state and background-fact updates (§§4–5, pp. 4–6). | Give corrections, revocations, forgetting, and suppression their own semantics and stronger anti-resurrection guarantees. |
| U5 | **Criticality is an intrinsic property of a memory class.** | Task/checkpoint/goal state is strong; background context is weaker (§4.4, p. 5; §5, p. 6). | Make criticality depend on the contemplated action: the same fact may be harmless in a trace and consequential when used to send, schedule, infer, or disclose. |
| U6 | **Background or long-term facts are naturally staleness-tolerant.** | §4.2, p. 4 uses them as the eventual-consistency example. | Treat user corrections and time-sensitive validity as orthogonal to semantic “backgroundness”; a long-lived fact may require immediate invalidation. |
| U7 | **Memory items are epistemically homogeneous.** | No distinction among stated facts, observations, or hypotheses; the main distinctions are critical/background and memory layer. | Carry claim form, source, evidence, confirmation status, and allowed uses as part of the memory object and retrieval contract. |
| U8 | **Similarity retrieval is the normal access path.** | §5, p. 6 says memory layers “often rely on vector embeddings and similarity searches.” | Query structured relations, temporal validity, authority, and exact entity bindings first; use embeddings only to propose candidates. |
| U9 | **Index coherence is mainly a synchronization problem.** | §5, p. 6 frames “consistent indexing and synchronization” as the concern. | Make index entries disposable projections of versioned canonical beliefs; require readers to validate the canonical version and policy before use. |
| U10 | **The application can label writes as critical before choosing a guarantee.** | §5, pp. 5–6 checklist begins “Identify critical semantic updates.” | Define explicit invariants and failure consequences, then derive the label; allow uncertainty about classification to be visible and tested. |
| U11 | **The user is a consumer of consistent behavior, not an actor in memory governance.** | User experience is mentioned only as an effect of correctness (§5, p. 6); there is no correction or inspection surface. | Make the subject of the memory the authority who can inspect, confirm, supersede, suppress, and trace beliefs. |
| U12 | **Semantic memory is not about third-party data rights.** | Admission, subject identity, and consent are absent throughout. | Partition the write path by who the claim is about, retaining work-level residue while structurally excluding third-party personal content. |
| U13 | **Replica staleness is the relevant notion of time.** | Eventual consistency addresses convergence after updates (§4.2, p. 4). | Model semantic aging, decay, expiry, and historical validity even when every replica is perfectly synchronized. |
| U14 | **System optimization can adapt invisibly.** | Dynamic consistency adaptation is proposed as future optimization (§6, p. 6). | Require consistency mode changes to remain explainable, bounded by stable invariants, or visible in response traces when they affect freshness. |

## 4. Questions the Paper Never Faced

These questions arise from Kivi’s users, product promises, and failure modes rather than from gaps filled with generic memory-system concerns. Each has at least two defensible answers; none is answered here.

### Admission, subject, and representation

1. **When one interaction contains the user’s work facts and another person’s personal facts, should the write boundary be decided per transcript, per candidate claim, per subject, or per derived use?** Kivi requires “read, not kept,” but mixed inputs make the atomic unit consequential. (Kivi §§2, 5.)
2. **When a derived work-level residue depends on discarded third-party content, how much provenance may survive without reconstructing the prohibited content?** A source transcript link aids auditability but can reopen access to what the write path promised not to keep. (Kivi §§5, 8–9.)
3. **When a candidate touches both an allowed and excluded category, should Kivi drop the whole candidate, redact it, generalize it, or split it?** The hard exclusion policy states categories, not boundary-case composition. (Kivi §2.)
4. **When the same sentence could be an entity fact, preference, and episode, should Kivi store one multi-typed belief, several linked beliefs, or force a single type?** This affects promotion, decay, retrieval, and correction. (Kivi §4.)
5. **When the user explicitly asks Kivi to remember a normally excluded subject, should the hard exclusion remain absolute, permit an exception, or retain only an instruction not to discuss/store it?** Kivi states a hard boundary and also makes stated information privileged; those principles can conflict. (Kivi §§2, 4.)

### Authority, contradiction, and correction

6. **When explicit user statements conflict with repeated observed behavior, should “stated” control action while “observed” remains visible, should the observation be suppressed, or should Kivi ask again?** Kivi separates the tiers but does not fully specify cross-tier contradiction. (Kivi §4.)
7. **When an inline correction changes an entity relation used by an in-flight response, should that response restart, patch itself, finish against its snapshot, or abstain?** (Kivi §§8–9.)
8. **When “That’s not me anymore” blocks re-derivation, should the suppression match exact content, a semantic neighborhood, a source set, a time range, or a category?** Narrow matching permits resurrection; broad matching can erase legitimate future change. (Kivi §9.)
9. **When “Forget” conflicts with auditability, should provenance history retain a tombstone, retain content under restricted access, or be irreversibly erased?** Kivi promises both reversibility/history and removal/suppression. (Kivi §§1, 9.)
10. **When a correction concerns another person’s work role, who has authority: the Kivi user, the source message, a newer application context, or recency alone?** (Kivi §§4–5, 9.)

### Retrieval and disclosure

11. **When Kivi retrieves all tiers but may disclose only some, may withheld observations still influence wording, ranking, tool choice, or abstention?** “Disclosure, not retrieval” leaves open whether covert influence counts as use. (Kivi §6.)
12. **When the quiet “Kivi noticed something here” affordance itself reveals that a sensitive pattern exists, should even the existence of withheld content be permission-gated?** (Kivi §6.)
13. **When regular dictation needs an entity spelling that was learned through excluded or third-party content, should lexical correction use it, forget it, or request confirmation?** The separate dictation path does not by itself settle provenance eligibility. (Kivi §§5, 7.)
14. **When a user asks a direct factual question in Anbu mode and the only support is an observation, should Kivi abstain, expose that it has withheld support, ask for a one-time reveal, or answer without the observation?** (Kivi §§6, 8.)
15. **When ranking memories, should explicitness, evidence count, recency, entity match, source quality, permission tier, or the cost of a wrong disclosure dominate?** Kivi specifies all these signals in different places but not their ordering. (Kivi §§4, 6, 8–9.)
16. **When one request spans dictation and Hey Kivi behavior, which retrieval contract applies to each part, and can memory retrieved for the interactive part leak into transcription?** (Kivi §7.)

### Error, user burden, and time

17. **When Kivi is uncertain, what should spend the limited confirmation budget: high probability of future reuse, high failure cost, high uncertainty, or a natural conversational moment?** (Kivi §8.)
18. **When the Why panel’s complete trace would expose excluded, withheld, or third-party information, should inspectability yield to non-disclosure, or should the trace show only policy-safe metadata?** (Kivi §§5–6, 8.)
19. **When an observation decays, should it become unavailable, merely rank lower, remain visible only in history, or trigger reconfirmation?** (Kivi §9.)
20. **When a hypothesis expires, should its supporting observations remain linked, should the question be regenerable, or should expiry suppress the same hypothesis for a period?** (Kivi §§4, 9.)
21. **When the user pins a memory that later conflicts with new explicit evidence, should the pin freeze content, freeze rank, require confirmation, or merely prevent decay?** (Kivi §9.)
22. **When Kivi is wrong because extraction, ranking, replica staleness, permission gating, or generation failed, should the repair and explanation differ by failure source?** A single correction action may not repair every layer. (Kivi §§8–9.)
23. **When a source transcript is edited or deleted outside Kivi, should derived memories be invalidated, retain their old provenance, or become unattributed?** Kivi makes provenance user-visible but does not define source lifecycle. (Kivi §§8–9.)
24. **When multiple devices or asynchronous application contexts update the same person’s memory, what must be immediately consistent: the belief, its tier, its provenance, its suppression status, its vector projection, or the user-visible trace?** This is the Kivi-specific decomposition of the paper’s generic “critical update.”

## 5. Evaluation Gap

### What the paper measured

The paper reports **no implementation, dataset, benchmark, experimental comparison, latency result, throughput result, staleness distribution, failure injection, user study, retrieval metric, or statistical analysis**. Its methodology is a qualitative review that “identifies relevant models, explains their guarantees, and discusses their trade-offs” (paper §3, p. 3). The “Results” section provides conceptual descriptions and examples (paper §4, pp. 4–5). The checklist says practitioners should test latency and monitor staleness, but the paper does not itself report those tests (paper §5, pp. 5–6).

Therefore, the paper’s evaluation cannot empirically distinguish **any** pair of design answers in D1–D21. It supplies precedent and vocabulary, not comparative evidence. More specifically:

| Decision pair that would score the same under the paper’s evaluation | Why the paper cannot distinguish them | Evidence the paper would need but does not provide |
|---|---|---|
| Global strong consistency vs. per-user single-writer serialization (D2, D11) | Both are compatible with the paper’s claim that critical reads should see ordered state; neither is implemented. | Deployment topology, concurrency workload, failover behavior, tail latency, and correctness under races. |
| Per-operation hybrid consistency vs. one global model (D4) | The hybrid is advocated conceptually, but no baseline is run. | Same workload under each policy, including classification errors and operational complexity. |
| Strong vs. causal vs. session consistency for Kivi corrections (D11–D13) | The paper defines the guarantees but never models a correction invariant or cross-device path. | Histories containing correction/read races, acceptance criteria, and observed stale-correction rate. |
| Eventual vs. bounded-staleness background memory (D14) | “Brief staleness” is never bounded or measured. | Staleness distribution, user-visible consequences, convergence failures, and a task-specific harm threshold. |
| Last-write-wins vs. supersession-with-history vs. multi-value conflict records (D9) | Replica visibility is discussed; semantic resolution is not. | Contradiction corpus, authority rules, resolution accuracy, auditability, and downstream answer effects. |
| Atomic record-plus-index writes vs. asynchronous indexing with version validation (D8) | Both could satisfy the phrase “consistent indexing and synchronization.” | Race tests across record/index versions, retrieval leakage after correction/suppression, latency and availability costs. |
| Vector similarity vs. structured, temporal, graph, or hybrid retrieval (D16) | Retrieval methods are mentioned only as surrounding architecture. | Recall/precision or task success on time-, entity-, provenance-, and contradiction-sensitive queries. |
| Retrieve-all-then-disclose vs. permission-filter-before-retrieval (D17) | Permission and epistemic tiers do not exist in the paper’s model. | Leakage tests, covert-influence tests, response utility, latency, and inspectability. |
| Persist-all vs. selective admission/non-retention (D6) | The paper treats captured semantic information as eligible memory. | Retention audit, privacy-policy violation rate, useful-residue recall, false drops, and user trust outcomes. |
| Hard delete vs. tombstone vs. suppress-rederivation (D10) | Negative updates and resurrection are absent. | Deletion propagation tests, re-extraction tests, audit requirements, and time-to-disappearance across projections. |
| Permanent memory vs. decay/expiry/reconfirmation (D20) | Semantic aging is not evaluated. | Longitudinal corpus with changing people/projects, stale-belief surfacing rate, and useful-memory loss. |
| Silent failure vs. qualification vs. abstention with trace (D18–D19) | No user-facing behavior is specified or studied. | Answer correctness, calibration, recovery time, confirmation burden, and user comprehension/trust. |
| Invisible dynamic adaptation vs. static explainable policy (D15) | Dynamic adaptation is only a future-work suggestion. | Switching policy, safety invariants, oscillation behavior, explainability, and end-to-end performance. |

### Metric blind spots even if the paper’s proposed checklist were executed

Suppose a practitioner followed the paper’s checklist and measured only retrieval latency and whether temporary inconsistencies misled agent logic (paper §5, pp. 5–6). Those metrics would still fail to distinguish:

- a system that answers correctly while retaining forbidden third-party information from one that never stores it (D6);
- a system that uses a withheld observation covertly from one that truly prevents its influence (D17);
- a system that displays a corrected belief but still retrieves its stale embedding from one with coherent correction propagation (D8, unless race-focused tests are added);
- a system that deletes a row but later re-derives it from old transcripts from one that records durable suppression (D10);
- a system that returns the same correct answer with no provenance from one whose answer is fully traceable (D18);
- a system that keeps an outdated but replica-consistent characterization forever from one that decays it (D20);
- a system that burdens the user with constant confirmations from one that budgets them (D19 and Kivi §8);
- a system whose replicas agree on the wrong semantic merge from one whose replicas expose unresolved contradiction (D9).

For these decisions, the paper provides **no evidence**, only a distributed-systems precedent that consistent visibility matters.

## Bottom line of the inversion

The paper’s core decision map is narrow but useful: identify a memory operation’s correctness, latency, staleness, and workload needs; then choose strong, causal, session, eventual, or hybrid consistency. Its load-bearing move is to vary guarantees by criticality rather than impose one global model.

Kivi’s hard questions sit mostly one layer above and one layer below that map. Above it: who is allowed to be remembered, what may be disclosed, who has authority to correct, and how trust fails. Below it: what the atomic belief is, how record and index versions move together, how suppression prevents resurrection, and how semantic aging differs from replica staleness. The paper does not decide those questions, and its evaluation supplies no evidence for choosing among their answers.
