# EverOS decision space for Kivi semantic memory

Scope: repository at `EverOS/`, HEAD `5076683` (2026-09-10 checkout). This is a map of questions and precedents, not a recommendation. A citation such as `src/...:10` is relative to `EverOS/`. “Inference” means the intention is not stated in the cited code. “Unclear” means the repository does not contain enough evidence.

## ORIENTATION — reported before analysis

### Where the real logic lives

- **Core memory behavior:** `src/everos/memory/`. It owns canonical memory models, ingest normalization, user/agent extraction pipelines, search planning/shaping, offline strategies, reflection, and Markdown-to-index cascade. The repository itself describes this layer as “models + extract + search + cascade + prompt_slots” (`docs/architecture.md:16`).
- **Use-case orchestration:** `src/everos/service/`. In particular, `memorize.py` coordinates the session lock and two pipelines, while `_boundary.py` owns buffer/merge/boundary/tail persistence (`src/everos/service/memorize.py:14-15`; `src/everos/service/_boundary.py:3-21`). `knowledge.py` is a separate document-memory use case (`src/everos/service/knowledge.py:1-9`).
- **Load-bearing storage mechanics:** `src/everos/infra/persistence/` and the older primitives still under `src/everos/core/persistence/`. These are not semantic-policy modules, but their atomicity, ordering, and schema choices freeze important decisions. The documented three-piece set is Markdown truth, SQLite coordination state, and a derived LanceDB/Milvus index (`docs/architecture.md:63-72`).
- **Algorithm boundary:** boundary detection, extraction, clustering, and ranking algorithms partly live in separately published `everalgo-*` packages rather than this repository (`docs/architecture.md:216-232`; `pyproject.toml:63-97`). Their prompts, model outputs, and some duplicate/contradiction semantics are therefore **unclear from this repo**.
- **Glue/adapters:** `src/everos/entrypoints/` is HTTP, CLI, and TUI wiring; the search route is a two-line dispatch (`src/everos/entrypoints/api/routes/search.py:16-22`), and the memorize route explicitly says it contains no business logic (`src/everos/entrypoints/api/routes/memorize.py:1-8`). `src/everos/component/` adapts LLM, embedding, rerank, tokenizer, parser, and observability providers.
- **Examples/integrations/evaluation, not product logic:** `examples/`, `use-cases/`, `deploy/`, and `benchmarks/`. Benchmark constants are evaluation-harness decisions, not runtime memory decisions, and are excluded from the runtime magic-number inventory.

### Data model and serialization

- Ingress canonicalizes messages to `message_id`, session/sender identity, role, UTC timestamp, multimodal `content_items`, derived text, and optional tool-call linkage (`src/everos/memory/models.py:36-64`). A request admits roles `user|assistant|tool` and content `text|image|audio|doc|pdf|html|email` (`src/everos/entrypoints/api/routes/memorize.py:75-110`).
- User memory kinds are episode, atomic fact, foresight, and profile; agent kinds are case and skill. The local domain models expose episode text, fact text, foresight plus evidence/time, and case intent/approach/quality (`src/everos/memory/models.py:94-120`, `155-181`, `215-247`, `270-299`). Knowledge topics/documents form a separate shared corpus (`docs/storage_layout.md:186-195`).
- Markdown is authoritative and user-visible; daily-log append stores episodes, atomic facts, foresights, and cases, while singleton/tree writers store profile, skill, and knowledge (`docs/storage_layout.md:77-94`). YAML frontmatter carries file identity/scope and marker-delimited bodies carry entries (`docs/storage_layout.md:96-146`).
- SQLite stores coordination rather than business memories: cascade queue, boundary buffer, MemCells, conversation status, clusters, knowledge metadata, and reflection reports (`docs/storage_layout.md:174-195`). The queue LSN is the ordering key (`src/everos/infra/persistence/sqlite/tables/md_change_state.py:34`).
- LanceDB/Milvus stores rebuildable retrieval rows. Episode and atomic-fact rows alone have `deprecated_by`; normal search suppresses non-null values (`docs/storage_layout.md:199-206`).
- Writes use a same-directory temporary file plus `os.replace`; atomic rename is only guaranteed within one filesystem (`docs/storage_layout.md:209-217`). No Alembic migration directory is present despite the dependency: schema evolution is handled in startup/storage code and compatibility branches. This absence is observed, while its reason is **unclear** (`pyproject.toml:38-41`).

### Main execution path, entry point to persistence

1. `POST /api/v2/memory/add` validates IDs, 1–500 messages, roles/content, and `defer_extraction`, then forwards a dict to the service (`src/everos/entrypoints/api/routes/memorize.py:89-136`, `174-189`). `/flush` addresses the same scoped session and forces the buffered boundary pass (`src/everos/entrypoints/api/routes/memorize.py:193-198`).
2. `memorize()` serializes calls by `(app, project, session)` because concurrent read/replace of the buffer otherwise loses messages (`src/everos/service/_session_lock.py:3-12`; `src/everos/service/memorize.py:194-200`).
3. Ingest normalizes content and generates deterministic-looking message IDs from session, millisecond timestamp, and position (`src/everos/memory/extract/ingest/id_gen.py:15`; `src/everos/memory/extract/ingest/service.py:42-92`).
4. The boundary stage reads prior buffer rows, merges fresh rows, deduplicates, sorts, and replaces the buffer (`src/everos/service/_boundary.py:101-173`, `442-459`). Chat mode drops tool rows and assistant tool-call carriers; agent mode keeps them (`src/everos/service/_boundary.py:230-237`).
5. A boundary result becomes a canonical MemCell shared by user and agent pipelines; chat mode runs only the user path (`src/everos/service/_boundary.py:21`; `src/everos/config/default.toml:158-164`).
6. The episode Markdown write completes before the request returns. Derived atomic facts, profiles, cases, skills, and optional foresights/reflections run later through OME strategies (`docs/how-memory-works.md:111-146`).
7. Filesystem changes enter the durable `md_change_state` SQLite queue; the cascade worker processes in LSN order, hashes entries, embeds changed content, and upserts the selected derived index (`docs/how-memory-works.md:93-109`; `src/everos/infra/persistence/sqlite/tables/md_change_state.py:34`).
8. Therefore write durability is strong at Markdown commit, but `/search` and `/get` are eventually consistent and may miss a just-flushed episode (`docs/architecture.md:85-109`; `docs/how-memory-works.md:151-174`).

## 1. DECISION INVENTORY

Each item is a question with at least two defensible answers.

### Ingress, ownership, and boundaries

1. **Should memory accept only text, or preserve multimodal/tool structure?** Repo answer: accepts strings or typed content items plus tool calls, derives text while retaining structured items (`src/everos/entrypoints/api/routes/memorize.py:64-112`; `src/everos/memory/models.py:55-64`). Placement: wire schema is hardcoded; parser/provider is pluggable. This suggests confidence in the envelope but not the parser. Assumes OpenAI-shaped agent traces and that parsing cost is acceptable. Kivi’s stated text-client scope makes most modalities surplus; tool/application context still matters, pushing toward a narrower, provenance-aware ingress rather than this broad media contract (`../kivi-semantic-memory-position.md:3`).

2. **Should third-party material be structurally barred from persistence, or allowed through general extraction?** Repo answer: all user, assistant, and tool content can enter the same canonical buffer; chat mode drops tool rows but there is no subject-of-memory or consent gate before storage (`src/everos/entrypoints/api/routes/memorize.py:100-110`; `src/everos/service/_boundary.py:230-237`). Placement: hardcoded role filtering, no pluggable privacy policy. Inference: it assumes sender ownership is an adequate memory boundary. That does not hold for Kivi, whose position requires third-party content to enter context but never the write path (`../kivi-semantic-memory-position.md:106-125`); difference pushes toward a separate context/write schema and auditable rejection.

3. **Is the deployment simultaneously capable of chat and agent memory, or does one process choose one mode?** Repo answer: one process runs `chat` (user pipeline only) or `agent` (user + agent pipeline), and changing it requires restart (`src/everos/config/default.toml:158-164`). Placement: configurable at deployment, not per request. Assumes homogeneous workload and operator control. Kivi has regular dictation versus Hey Kivi rights per request (`../kivi-semantic-memory-position.md:181-199`), so the assumption does not hold; difference pushes toward request/surface-specific retrieval and write policies.

4. **Where is a conversational episode boundary decided: client, fixed size, or model?** Repo answer: an `everalgo` boundary detector decides, forced at 65,536 tokens or 500 messages; `/flush` gives the caller an override (`src/everos/config/default.toml:153-156`; `src/everos/entrypoints/api/routes/memorize.py:193-198`). Placement: algorithm pluggable only through an external package; hard caps configurable. Assumes sessions are ordered and can wait on an LLM. Kivi transcripts are replayed through its own interface; applicability is unclear until the unit of provenance and correction is chosen.

5. **Should repeated input be appended, rejected, or coalesced?** Repo answer: buffered and fresh messages are merged, deduplicated by message identity, sorted, then the whole scoped buffer is replaced (`src/everos/service/_boundary.py:113-114`, `442-459`). Placement: hardcoded. Assumes stable IDs/timestamps and that duplicate delivery is normal. This likely holds for replayed Kivi transcripts, but Kivi also needs a visible extraction event trail, which this message-level dedupe does not provide.

6. **What ordering guarantees exist under concurrent ingest?** Repo answer: FIFO per-session locks serialize `(app, project, session)` mutations, avoiding lost tail updates; partition locks grow with live keys (`src/everos/service/_session_lock.py:3-12`; `src/everos/memory/_partition_locks.py:18-53`). Placement: hardcoded correctness mechanism with configurable 360-second outer timeout. Assumes ordering only matters inside a session, not globally. That is compatible with transcript-scoped Kivi ingestion, but cross-source corrections would need an order this repo never defines.

### Representation and persistence

7. **Should durable truth be an opaque database or inspectable files?** Repo answer: Markdown is truth; SQLite is coordination; vector/BM25 is disposable projection (`docs/storage_layout.md:6`, `174-206`). Placement: architectural hardcode, with only the derived-index backend pluggable. This reveals high confidence in local inspectability and rebuildability. Assumes small-team/local filesystem scale, tolerable file rewrite cost, and one filesystem boundary. It aligns strongly with Kivi’s visibility/provenance requirement, but Kivi’s individual-memory editing and suppression semantics demand finer audit fields than current Markdown guarantees.

8. **Are memories first-class typed beliefs or narrative/utility artifacts?** Repo answer: episodes, atomic facts, foresights, aggregate profile, agent cases, and skills (`src/everos/memory/models.py:94-299`). Placement: types are hardcoded; models allow extra algorithm fields (`src/everos/memory/models.py:120`, `181`, `247`, `299`). This suggests confidence in the taxonomy but lower confidence in complete field shape. It assumes useful memory includes inference (profile/foresight) and agent-performance abstractions. Kivi’s entity/preference/episode × stated/observed/hypothesised axes are not represented (`../kivi-semantic-memory-position.md:68-110`); the mismatch pushes toward epistemic tier and source evidence as primary schema, not generic `extra` fields.

9. **Should every belief carry source-level provenance?** Repo answer: derived objects carry `session_id` and `parent_id`, cases carry parent/session, skills carry source case IDs, but response DTOs do not expose transcript spans/evidence uniformly (`src/everos/memory/models.py:116-118`, `178-179`, `244-245`, `296-297`; `src/everos/memory/search/dto.py:225-235`). Placement: partial hardcoded linkage. Assumes session/parent IDs are sufficient operational provenance. Kivi requires the actual source transcript behind every belief and a Why trace (`../kivi-semantic-memory-position.md:233-268`), so this is materially insufficient.

10. **When content changes, rewrite truth or append a new immutable version?** Repo answer: daily files are read/merged/rewritten atomically, while reflection records supersession with `deprecated_by`; knowledge replacement uses backup, overwrite/upsert, and restore on failure (`docs/storage_layout.md:209-217`; `src/everos/service/knowledge.py:540-602`). Placement: per-kind hardcode, not a common versioning abstraction. Assumes audit needs differ by kind. Kivi says demotion/supersession are ordinary operations and deletions should not erase history (`../kivi-semantic-memory-position.md:232-248`); only reflection resembles that model.

11. **What happens on contradiction: keep both, overwrite, or supersede with lineage?** Repo answer: reflection deprecates source episodes/facts in favor of a merged narrative, and normal search hides deprecated rows (`docs/storage_layout.md:199-202`; `tests/integration/test_reflection_integration.py:383-400`). User-profile conflict semantics are inside `everalgo` and are **unclear**. Placement: hardcoded for reflection; absent as a general belief operation. Assumes contradiction is mainly consolidation, not user correction. Kivi explicitly distinguishes contradiction, correction, demotion, and suppression, so the repo supplies only partial precedent.

12. **Should a user rejection delete evidence or prevent re-derivation?** Repo answer: no general suppression/tombstone model is visible; deletion and reflection deprecation are storage operations. Placement: missing/incomplete rather than a deliberate alternative. Kivi requires “not me anymore” to block re-derivation (`../kivi-semantic-memory-position.md:239-248`), so this repo never answers the key recurrence question.

### Extraction and evolution

13. **Should enrichment block the request or evolve offline?** Repo answer: episode Markdown is synchronous; facts/profile/cases/skills/foresight/reflection are OME events after commit (`docs/how-memory-works.md:111-146`). Placement: architectural hardcode with per-strategy enable/schedule/retries configurable. Assumes eventual enrichment is acceptable and reduces request latency/failure coupling. Kivi may need excluded-candidate counts and source traces immediately (`../kivi-semantic-memory-position.md:47-49`, `123-125`); the difference pushes toward making policy enforcement synchronous even if enrichment remains offline.

14. **Should predicted future needs be stored?** Repo answer was reversed: `extract_foresight` exists but now ships disabled because it incurred one LLM call per sender per MemCell for data no route or prompt consumed (`src/everos/config/default_ome.toml:35-39`; `CHANGELOG.md:469-481`). Placement moved from default behavior to opt-in plugin-like strategy. This is a high-confidence reversal on cost/product utility. Kivi explicitly rejects plausible inference and durable guesses (`../kivi-semantic-memory-position.md:45-62`), so the difference pushes further away from foresight-as-belief.

15. **Should profiles refresh continuously, periodically, or only on confirmation?** Repo answer: profile extraction minimum and interval are both 1, so every eligible MemCell can re-extract; operators can disable the strategy (`src/everos/memory/strategies/extract_user_profile.py:26`, `74-79`, `217-239`). Placement: thresholds hardcoded, strategy configurable. Assumes LLM aggregation is acceptable truth maintenance. Kivi forbids self-promotion and psychological characterization, requiring explicit confirmation for tier promotion (`../kivi-semantic-memory-position.md:91-110`); this assumption does not hold.

16. **Should old memories decay, be consolidated, or remain equally live?** Repo answer: weekly lossy reflection is available but disabled; when enabled it merges cluster members and hides originals, while ordinary retrieval has no general time decay (`src/everos/config/default_ome.toml:50-57`; `docs/how-memory-works.md:132-146`). Placement: optional scheduled strategy. Assumes consolidation is riskier than accumulation. Kivi requires observation decay and hypothesis expiry, not just episode merging (`../kivi-semantic-memory-position.md:237-242`); those questions remain unanswered.

17. **Should low-quality agent experience be retained and clustered?** Repo answer: cases below quality 0.2 are skipped before embedding/clustering (`src/everos/memory/strategies/trigger_skill_clustering.py:15-39`, `79`). Placement: hardcoded mirror of external extractor behavior, revealing inherited confidence rather than local evaluation. Assumes model quality scores are calibrated and low-quality traces have negative value. This is not directly relevant to Kivi’s user semantic memory; if reused for observations, Kivi would need explainable evidence rather than an opaque scalar.

### Retrieval, ranking, exposure, and failure

18. **Does the caller choose retrieval strategy?** Repo answer: yes—keyword, vector, hybrid, agentic, and LLM-multiround are wire-level methods; hybrid is default (`src/everos/memory/search/dto.py:31-49`, `92-105`). Placement: pluggable per request, suggesting low confidence in one universal ranking answer. Assumes technical callers can select semantics. Kivi’s user-facing permission dial is about disclosure, not retrieval (`../kivi-semantic-memory-position.md:157-178`); exposing ranker choice would solve a different problem.

19. **Retrieve all memory then gate disclosure, or filter before retrieval?** Repo answer: query filters select owner/scope/kind/deprecation before retrieval, and no disclosure tier exists (`src/everos/memory/search/filters.py:1-38`; `src/everos/memory/search/dto.py:83-114`). Placement: hardcoded security/storage filtering. Kivi says retrieve everything and separately record what was withheld (`../kivi-semantic-memory-position.md:157-177`), so this architecture lacks the required second-stage disclosure decision and trace.

20. **What gets returned and in what order?** Repo answer: ranked `/search` returns separate arrays for episodes, profiles, agent cases, agent skills, and unprocessed messages; each ranked item has a score, while `/get` is a paginated list sorted by timestamp/updated time (`src/everos/memory/search/dto.py:146-299`; `src/everos/memory/get/dto.py:77-85`). Placement: response shape hardcoded; method and top-k configurable. Assumes callers can reconcile multiple arrays and scores. Kivi needs used/withheld/source attribution per response, which is absent.

21. **Should unprocessed recent messages be searchable?** Repo answer: yes, returned as an explicit `unprocessed_messages` array scoped only by session because buffer rows lack owner attribution (`src/everos/memory/search/dto.py:238-287`; `src/everos/memory/search/manager.py:289-293`). Placement: hardcoded exposure. Assumes freshness can outrank semantic processing and that session identity is authorization enough. For Kivi this could bridge immediate dictation context, but it conflicts with structural non-retention unless third-party content is segregated.

22. **How is “unlimited” retrieval handled?** Repo answer: `top_k=-1` is accepted, then internally capped (episodes 100, agent results 10) with extra low-score filtering in unlimited mode (`src/everos/memory/search/dto.py:94`, `123-126`; `src/everos/memory/search/manager.py:106-128`). Placement: magic hardcode behind a misleading wire sentinel. Assumes bounded context/cost matters more than literal unlimited semantics. Kivi’s retrieval-all-for-disclosure trace makes this especially consequential: “all” cannot silently mean 100 without changing the trust claim.

23. **On missing embedding/reranker, fail or degrade?** Repo answer: optional providers produce capability tiers; dense recall becomes empty if embedding is absent, while some search modes/fallbacks continue (`src/everos/memory/search/manager.py:668-690`; `CHANGELOG.md:669-713`). Placement: deliberate pluggable degradation. Assumes partial relevance is better than no answer. Kivi explicitly prefers actionable abstention over plausible output (`../kivi-semantic-memory-position.md:203-229`); silent degradation would need to become visible evidence.

24. **On decider failure, abstain or return a deterministic fallback?** Repo answer: retry three times, then choose a fallback core of three candidates (`src/everos/config/default.toml:105-109`; `src/everos/config/settings.py:292-311`). Placement: configurable. Assumes recall fallback is safer than empty. Kivi’s no-guess rule pushes toward making this failure visible; whether raw recall is a “guess” remains a product question.

25. **Are similarity scores comparable enough to drive confidence?** Repo answer: only hybrid/agentic are treated as calibrated `[0,1]`; keyword BM25 and single-route vector scores are explicitly not comparable, and a 0.6 hit threshold applies only to calibrated methods (`src/everos/config/default.toml:226-230`; `src/everos/memory/search/manager.py:148-153`, `261-278`). Placement: threshold configurable, calibration class hardcoded. Kivi needs confidence to govern abstention, observation status, and disclosure; this repo offers retrieval telemetry, not epistemic confidence.

26. **Should failures block durable writes?** Repo answer: Markdown failure blocks success; index failure does not, because the SQLite queue replays it later (`docs/architecture.md:107-109`). Cascade retries eventually become permanent failure after 12 total attempts (`src/everos/memory/cascade/worker.py:15-23`, `126`, `777-833`). Placement: hardcoded failure budget, operational repair via CLI. Assumes losing immediate searchability is cheaper than losing the memory. That likely holds for Kivi, provided the user-facing trace can distinguish “known but not currently retrievable.”

27. **What is idempotent?** Repo answer: message-buffer merge dedupes IDs; index writes upsert by ID; knowledge DELETE is explicitly idempotent; duplicate knowledge create is a conflict and PUT is replacement (`src/everos/service/_boundary.py:442-459`; `src/everos/infra/persistence/index/protocols.py:34`; `src/everos/service/knowledge.py:181`, `504-523`). Placement: inconsistent per operation, suggesting pragmatic rather than unified command semantics. Kivi correction/promotion/demotion events need explicit event identity; this repo has no general event-idempotency contract.

## 3. WHAT THE HISTORY SAYS

Reversals are the highest-value signal because they show an answer failed under use, not merely that another answer was imaginable.

### Reversed or rewritten decisions

- **Highest-value reversal — foresight default:** enabled extraction became disabled-by-default. The stated reason was not correctness but a full LLM call per sender per MemCell producing write-only data with no search route or prompt consumer (`CHANGELOG.md:467-481`; `src/everos/config/default_ome.toml:35-39`).
- **Highest-value reversal — result-count contract:** pre-2026-08-06 the decider could let “core” results exceed caller `top_k`; current `core_overflow=false` preserves the cap (`src/everos/config/default.toml:107`; `src/everos/config/settings.py:298-311`). This exposes a prior conflict between semantic completeness and API predictability.
- **Highest-value reversal — `/get` filters:** an earlier design banned AND/OR combinators, but current code permits them because the legacy system supported them and the engine had no reason not to (`src/everos/memory/get/dto.py:17-21`). This is explicitly backward compatibility plus removal of an artificial constraint.
- **Backend abstraction added late:** commits `7849535`, `de56331`, and feature `9d0ed5b` separated index contracts/routing and added Milvus. The current architecture forbids ports from importing concrete backends (`pyproject.toml:235-273`). This implies the original LanceDB-shaped answer stopped being sufficient.
- **API versioning rewritten with compatibility alias:** `/api/v2` became canonical while `/api/v1` resolves to the same handlers (`CHANGELOG.md:736-736`, `800-803`; `tests/unit/test_entrypoints/test_api/test_api_versioning.py:1-8`). This is backward compatibility, not two semantic versions.
- **Knowledge foreign-key answer reversed:** the FK on `knowledge_topics.doc_id` was removed because delete ordering raced (`CHANGELOG.md:1020-1027`). Consistency moved from database-enforced relation to application/cascade coordination.
- **Retry behavior rewritten:** rerank retries spun immediately until commit `5076683`; they now exponentially back off (`src/everos/component/rerank/_errors.py:16-33`).

### Recurring bug-report themes

- **Eventual-consistency races recur:** skill extraction could dead-letter before a newly written case reached LanceDB; current strategy/history describes loading Markdown directly so it no longer races the index (`CHANGELOG.md:175-180`; `src/everos/memory/strategies/trigger_skill_clustering.py:128`). Public issue #275 records the same defect class: <https://github.com/EverMind-AI/EverOS/issues/275>.
- **Cascade/LanceDB maintenance generated a series, not a single bug:** stalled table-handle resolution, prune/rebuild commit races, false failure counters, cleanup starvation, and disk growth appear across the 1.2.2–1.2.3 notes (`CHANGELOG.md:544-633`, `356-423`). This is recurring evidence that “embedded, rebuildable index” lowers data-loss cost but not operational complexity.
- **Retrieval/API mismatch recurs:** agent search broke because a user-only `deprecated_by` predicate was applied to agent tables (`CHANGELOG.md:883-891`); public issue #131 reported that `/get` omitted full episode content and substituted a 200-character summary, and issue #58 reported content visible in listing but not retrievable. Current DTOs now expose full `episode` (`src/everos/memory/get/dto.py:127-142`). Issues: <https://github.com/EverMind-AI/EverOS/issues/131>, <https://github.com/EverMind-AI/EverOS/issues/58>.
- **Action memories have no lifecycle:** public issue #143 reports completed tasks resurfacing and being re-executed because there is no status, session-aware relevance, or decay. That absence is visible in current episode/search DTO fields (`src/everos/memory/search/dto.py:167-181`). Issue: <https://github.com/EverMind-AI/EverOS/issues/143>.
- **Single-loop/backpressure remains a failure surface:** public issue #316 reports API/health stalls under knowledge uploads plus background extraction. The repo’s large lock/semaphore/time-budget surface corroborates the class, but the issue’s proposed root cause remains an external report, not proven here (`src/everos/config/default.toml:182-188`; `src/everos/infra/ome/config.py:147-150`). Issue: <https://github.com/EverMind-AI/EverOS/issues/316>.

### Shortcuts and admissions

- `_dispatch/_state.py` admits its `sys._getframe` search for a `Runner.run` frame is a TODO (`src/everos/infra/ome/_dispatch/_state.py:10`). This is incomplete work, not a semantic design.
- There is no automatic Markdown grep fallback when the derived index is unavailable (`docs/how-memory-works.md:176-180`). This is an acknowledged missing degradation path.
- Timestamp seconds-vs-milliseconds auto-detection and permissive legacy entry sequence widths are compatibility heuristics (`src/everos/entrypoints/api/routes/memorize.py:101-107`; `src/everos/core/persistence/markdown/entries.py:69`).
- Domain models use `extra="allow"` to tolerate algorithm schema expansion (`src/everos/memory/models.py:120`, `181`, `247`, `299`). That is compatibility slack, not evidence that extra fields have designed semantics.
- LanceDB is narrowly pinned around known compaction/storage regressions, with explicit workaround and validation debt (`pyproject.toml:28-37`). This is a dependency constraint born from incidents.

## 4. UNEXAMINED DEFAULTS

These have no nearby comment, test that compares a substantive alternative, or traceable issue rationale. They may be framework inheritance rather than deliberate product design.

- **Default owner scope is literal `"default"`.** Alternative not tried: require explicit tenant/app/project on every request (`src/everos/memory/search/dto.py:88-89`; `src/everos/entrypoints/api/routes/memorize.py:117-128`).
- **Hybrid is the default search method.** Alternative not tried at the product boundary: choose based on query/corpus or hide methods behind one calibrated policy (`src/everos/memory/search/dto.py:92-94`).
- **Profiles are excluded unless `include_profile=true`.** Alternative not tried: always retrieve profile then disclose selectively (`src/everos/memory/search/dto.py:104`).
- **`sort_order=desc` and page size 20.** Alternative not tried: stable cursor ordering or relevance/time mixture (`src/everos/memory/get/dto.py:77-85`).
- **Profile and skill silently override requested timestamp sort to `updated_at`.** Alternative not tried: reject an invalid sort or expose kind-specific sort fields (`src/everos/memory/get/dto.py:79-82`).
- **Content items allow `extras`, while the enclosing DTO forbids unknown fields.** Alternative not tried: versioned extension schemas or forbid opaque provider metadata (`src/everos/entrypoints/api/routes/memorize.py:75-86`).
- **`sender_id` becomes owner identity.** Alternative not tried: explicit subject-of-memory separate from speaker, essential when a user quotes another person (`src/everos/entrypoints/api/routes/memorize.py:89-98`).
- **Message IDs are derived from session, timestamp, and array index.** Alternative not tried: require upstream stable IDs or hash semantic content (`src/everos/memory/extract/ingest/id_gen.py:15`).

- **No status/evidence count/first-seen/last-confirmed fields on user memories.** Alternative not tried: make epistemic state first-class rather than `extra` metadata (`src/everos/memory/models.py:94-247`).
- **A local filesystem and single memory root define the unit of authority.** Alternative not tried: per-user cryptographic/logical stores or append-only event log (`docs/storage_layout.md:10-56`).

## 5. QUESTIONS THIS REPO NEVER FACED

Derived from Kivi’s positioning; these are questions, not proposed answers.

1. How is the **subject** of a candidate memory identified independently of the message sender, especially when the user quotes or summarizes another person? EverOS equates sender-derived ownership with memory ownership (`src/everos/entrypoints/api/routes/memorize.py:89-98`); Kivi requires non-retention of others (`../kivi-semantic-memory-position.md:106-125`).
2. At what exact stage does a deterministic exclusion classifier run, and what audit record proves each sensitive/third-party candidate was dropped? EverOS exposes no candidate-rejection model (`src/everos/memory/models.py:85-91`); Kivi requires reasoned drop counts (`../kivi-semantic-memory-position.md:45-62`).
3. Is the exclusion taxonomy fixed, jurisdiction-specific, user-configurable, or versioned—and what happens when its version changes against old transcripts?
4. What makes a memory **stated**, **observed**, or **hypothesised**, and can storage grammar prevent a question from being asserted as fact? EverOS types content by utility, not epistemic authority (`src/everos/memory/models.py:94-299`; `../kivi-semantic-memory-position.md:68-110`).
5. What is the confirmation event schema, who/what may issue it, and is confirmation scoped to wording, proposition, entity, or time?
6. How are contradictory sources resolved when both are explicit user statements—recency, specificity, context, or an unresolved state?
7. What does “that’s not me anymore” suppress: one phrasing, a normalized proposition, an embedding neighborhood, a rule, or every re-derivation from named transcripts (`../kivi-semantic-memory-position.md:239-248`)?
8. How do observations decay, and can old evidence still be inspected after it loses disclosure standing? EverOS has consolidation/deprecation but not behavioral decay (`docs/storage_layout.md:199-202`).
9. How is a per-request Daari invitation detected without recreating the rejected “infer permission from tone” behavior (`../kivi-semantic-memory-position.md:166-178`)?
10. Can retrieval genuinely fetch all tiers while disclosure gates the answer, and how is a withheld item represented without leaking its content?
11. What exact trace binds response clauses to used memories, retrieved-but-unused memories, withheld memories, and source transcript spans? EverOS returns scores but no use/withhold trace (`src/everos/memory/search/dto.py:270-299`).
12. How are regular dictation and Hey Kivi given structurally distinct stores/ports so dictation cannot query observations even by bug (`../kivi-semantic-memory-position.md:185-206`)?
13. What is the confirmation-prompt budget unit (week, device, user, workspace), how is value estimated, and how does unused budget carry over?
14. What constitutes an actionable abstention, and how does the system distinguish “not stored,” “withheld,” “index lag,” “provider unavailable,” and “searched but no match”?
15. Who can edit/demote/remove a belief in shared-device or organizational contexts, and what provenance survives removal?
16. Do hypotheses expire by wall time, evidence freshness, request count, or explicit resolution, and what happens to their source trace?
17. How are exact lexical/entity memories separated from semantic beliefs at schema and capability level, not merely by filters?
18. How can evaluation measure non-retention, calibration, and revisability—not just recall accuracy—without storing the prohibited content in fixtures/logs?

## 6. WHAT THE TESTS DON'T COVER

These are decisions for which a materially different answer could still leave the observed suite green.

- **Kivi’s privacy boundary:** tests validate path-safe IDs and content shapes, not whether third-party or sensitive facts are rejected before persistence (`tests/unit/test_entrypoints/test_api/test_routes/test_memorize_route_validation.py:31-55`; `src/everos/entrypoints/api/routes/memorize.py:25-55`).
- **Epistemic tier correctness:** no stated/observed/hypothesised fields exist, so no test can distinguish explicit user truth from inferred pattern (`src/everos/memory/models.py:94-247`).
- **Proposition-level contradiction:** reflection tests verify deprecation mechanics and search hiding, not whether the merged narrative resolved contradictions correctly (`tests/integration/test_reflection_integration.py:383-400`, `665-673`).
- **Suppression against re-derivation:** deleting/demoting a memory and replaying the same transcript is not a modeled scenario; another implementation that immediately recreates it would pass.
- **Disclosure versus retrieval:** search tests distinguish filters/rankers but there is no permission-tier stage; retrieving less and withholding more are observationally indistinguishable to the suite (`src/everos/memory/search/manager.py:191-281`).
- **Actionable abstention:** provider-degradation tests validate continued service/error mapping, not a user-facing explanation of what was searched or missing (`tests/unit/test_service/test_knowledge_search_degradation.py:1`; `tests/integration/test_api/test_provider_error_mapping.py:1`).
- **Semantic truth of extraction:** most tests mock `everalgo`/LLM outputs and verify wiring/persistence. Only marked live tests exercise real model behavior, and the default command excludes them (`pyproject.toml:168-190`; `tests/e2e/test_search_endpoint_e2e.py:352-397`). Thus taxonomy, factuality, inference boundaries, and duplicate wording receive precedent, not evidence.
- **Scale beyond local/small-team assumptions:** concurrency race tests reach 16 writers (`tests/unit/test_core/test_persistence/test_markdown/test_writer_race.py:67-100`), but they do not establish behavior for thousands of simultaneous users, network filesystems, multi-process writers, or cross-region storage.
- **Literal read-your-write:** the suite accepts the documented eventual index path; a design with 15-second lag and one with sub-millisecond lag can both pass if tests poll/reconcile (`docs/how-memory-works.md:151-174`).
- **Ranking calibration:** tests exercise result order and configuration plumbing, but the repository cites no held-out calibration study for radius 0.5, hit 0.6, cluster 0.65, or the decider pool sizes (`src/everos/memory/search/manager.py:116-121`; `src/everos/config/default.toml:95-109`, `190-196`, `226-230`).
- **User trust surface:** no test verifies that a normal user can understand why a memory was stored, used, withheld, changed, or discarded. The API supplies request IDs and scores, not the Why panel required by Kivi (`src/everos/memory/search/dto.py:293-299`; `../kivi-semantic-memory-position.md:233-268`).
- **Longitudinal person-change behavior:** reflection tests cover merge lineage, but no months-long simulation distinguishes a revisable colleague model from a stale profile (`tests/integration/test_reflection_integration.py:441-682`).
- **Prompt-budget burden:** nothing measures the cost to a user of confirmations because confirmation prompts are not part of this system.
