# Engram Decision Space for Kivi

## Scope and method

This report maps questions and precedents; it does not recommend answers. “Engram” means commit `7cbf01b` on `main`. “Kivi” means the text-client semantic-memory system in `../kivi-semantic-memory-position.md`, whose defining constraints are calibrated disclosure, non-retention of third-party personal content, and user-reversible beliefs (`../kivi-semantic-memory-position.md:19-25`). “Holds for Kivi” below is an explicit comparison or inference, not a recommendation.

I read all production code in `internal/store`, `internal/mcp`, `internal/sync`, and `internal/project`; the entry/config paths in `cmd/engram`, `internal/server`, `internal/cloud/config.go`, `internal/cloud/autosync`, `internal/cloud/remote`, `internal/cloud/cloudserver`, and `internal/cloud/cloudstore`; the codebase guides; and tests by behavior cluster. I sampled plugin lifecycle code and issue-linked regressions. I skipped generated `*_templ.go`, bundled HTMX/Pico assets, images, most TUI rendering, release plumbing, and installer details not implicated by history. Thus “every magic number” means every behavioral threshold found in the memory, retrieval, conflict, persistence, sync, and ingestion paths—not cosmetic layout dimensions or test-fixture counts.

## Orientation

### Core versus edges

The local memory core is `internal/store`: the repository itself calls it the source of truth and assigns it SQLite, FTS5, sessions, observations, prompts, relations, mutations, dedupe, topic upserts, and diagnostics (`docs/codebase/memory-core.md:3-5`; `docs/codebase/repository-map.md:30-32`). `internal/mcp` is the semantic API for agents and translates tool calls into store operations (`docs/codebase/repository-map.md:32-33`). `internal/sync` owns chunk export/import, while `internal/cloud/autosync` owns leases, push/pull, cursors, backoff, and degraded state (`docs/codebase/repository-map.md:34-38`).

`cmd/engram` is composition and CLI parsing; `internal/server` is a local JSON adapter; `internal/tui` and `internal/cloud/dashboard` are presentation; `internal/setup` and `plugin/*` are integration glue; and Obsidian is an export/integration surface (`docs/codebase/repository-map.md:30-46`). Cloud persistence is a second core only for hosted replication: `internal/cloud/cloudstore` projects the replicated state into Postgres (`docs/codebase/repository-map.md:38-40`).

### Frozen data model

The local model has sessions; observations; raw user prompts; FTS mirrors; relations between observations; an ordered sync mutation journal; deferred/dead apply rows; enrollment; and sync state (`internal/store/store.go:103-137,261-274,324-364`; `docs/codebase/memory-core.md:29-40`). An observation freezes `type`, free-text `title` and `content`, optional tool/project/topic, scope, revision and duplicate counts, last-seen/review timestamps, pin state, and soft deletion (`internal/store/store.go:118-137`). It has no subject, epistemic tier, evidence edge to transcripts, confirmation event, suppression, exclusion reason, or disclosure permission; that absence matters for Kivi (inference from `internal/store/store.go:118-137` versus `../kivi-semantic-memory-position.md:97-102,236-248`).

FTS5 externally indexes observation title/content/tool/type/project/topic and prompt content/project, using the trigram tokenizer (`internal/store/store.go:2313-2335`). Sync serializes sessions, observations, prompts, and relations separately; delete/hard-delete are payload flags and IDs are portable string `sync_id`s (`internal/store/store.go:468-517`). The cloud schema separates principals/tokens/grants/audit from chunks, materialized sessions, controls, and mutations (`internal/cloud/cloudstore/cloudstore.go:584-784`).

### Main execution path

The agent—not an extractor—decides what enters memory, then calls `mem_save`, `mem_session_summary`, `mem_save_prompt`, or passive capture (`docs/codebase/memory-core.md:7-23`). MCP resolves project identity, creates or binds a session, and sends writes through one bounded serial queue (`internal/mcp/write_queue.go:12-88`). `AddObservation` redacts `<private>` regions, validates non-empty title/content, normalizes project/scope/topic, performs topic upsert or exact-window dedupe, writes SQLite and FTS-triggered state, then journals a sync mutation when enrolled (`internal/store/store.go:2912-3051`; `internal/store/store.go:2337-2358`). After save, MCP performs non-fatal FTS candidate detection and exposes pending judgments (`internal/mcp/mcp.go:1449-1503`). Autosync acquires a lease, pushes ordered local mutations, pulls by cursor, applies them, and records degraded/healthy state (`internal/cloud/autosync/manager.go:1-10,79-95`).

Retrieval is progressive: context/search first and full observation hydration separately (`docs/codebase/memory-core.md:25-27,50`). `mem_search` defaults to project resolution, supports explicit all-project and personal cross-project behavior, returns compact previews, and annotates relations (`internal/mcp/mcp.go:1083-1160`). Search is lexical FTS/LIKE, not embedding retrieval (`internal/store/store.go:4162-4172,4246-4269`).

### Config surface

Public process configuration comprises `ENGRAM_DATA_DIR`, `ENGRAM_PORT`, `ENGRAM_SOCKET`, `ENGRAM_PROJECT`, `ENGRAM_HTTP_TOKEN`, `ENGRAM_TIMEZONE`, `ENGRAM_AGENT_CLI`, `ENGRAM_CLOUD_AUTOSYNC`, `ENGRAM_CLOUD_SERVER`, `ENGRAM_DATABASE_URL`, `ENGRAM_CLOUD_HOST`, `ENGRAM_CLOUD_MAX_PUSH_BYTES`, `ENGRAM_CLOUD_TOKEN`, `ENGRAM_CLOUD_INSECURE_NO_AUTH`, `ENGRAM_CLOUD_ALLOWED_PROJECTS`, `ENGRAM_JWT_SECRET`, `ENGRAM_CLOUD_ADMIN`, and managed-token pepper; precedence and meanings are documented in the command usage (`cmd/engram/main.go:3242-3286`; socket is parsed at `cmd/engram/main.go:856`). Cloud config also exposes CORS origins, DB pool, port, bind host, and max body bytes as code-level fields (`internal/cloud/config.go:9-38`).

Per-call configuration includes project/scope/type, all-project selection, search limit and `all|any` match mode, context section caps/byte cap/compact mode, timeline before/after, hard delete, topic key, pin/review actions, conflict list/scan limits, dry-run/apply, semantic runner, concurrency, per-call timeout, candidate threshold and semantic cap (`cmd/engram/main.go:3177-3237`; `cmd/engram/conflicts.go:295-469`; `internal/server/server.go:1153-1199`). Store `MaxObservationLength`, context/search maxima, and dedupe window are code configuration but not environment variables (`internal/store/store.go:548-579`). Candidate limit/BM25 bounds are pluggable through `MCPConfig`, while decay windows are hardcoded (`internal/mcp/mcp.go:1452-1461`; `internal/store/store.go:306-319`).

### What tests exercise

The suite heavily exercises schema migration/legacy rows, FTS, exact dedupe/topic revision, project normalization/ownership, soft/hard deletion, review lifecycle, relation judgment, cross-project rejection, deferred/dead relation replay, mutation ordering/idempotency, cloud enrollment, and LWW import. Examples include relation candidate thresholds and concurrency (`internal/store/relations_test.go:359-440`), semantic idempotency (`internal/store/judge_by_semantic_test.go:82-204`), relation defer/replay (`internal/store/relation_sync_integration_test.go:211-383`), legacy-null handling (`internal/store/legacy_null_project_test.go:49-176`), and context-default assertions (`internal/store/store_test.go:14277-14309`). MCP tests cover write serialization/cancellation (`internal/mcp/write_queue_test.go:16-195`) and tool contracts; server/sync/cloud tests cover HTTP envelopes, auth, chunk/mutation transport, and replication boundaries.

Tests provide unusually strong evidence for operational invariants. They provide little evidence for extraction quality, privacy classification, epistemic tiers, user-facing disclosure, source-grounded answers, abstention, or re-derivation suppression because Engram does not model those things (inference from the model at `internal/store/store.go:118-137` and Kivi’s required demonstrations at `../kivi-semantic-memory-position.md:277-287`).

## 1. Decision inventory

### Admission and capture

1. **Who decides what is memorable: an upstream agent/user, or a memory-owned extractor?** Engram answers “the agent,” with optional prompt/passive capture; persistence accepts already-curated observations (`docs/codebase/memory-core.md:7-23`). This is deliberate protocol design, encoded in agent tools rather than pluggable extraction. It assumes a cooperative coding agent, structured work artifacts, and tolerable omission. Kivi instead requires automatic candidate extraction plus a hard exclusion check and drop log (`../kivi-semantic-memory-position.md:45-49`); the difference pushes the decision upstream into a safety-critical ingestion subsystem Engram never needed.

2. **Should raw user input be retained alongside curated memory?** Engram stores user prompts as first-class retrievable records and can auto-capture the current prompt during save (`internal/store/store.go:261-274`; `internal/mcp/mcp.go:1421-1430`). This is hardcoded product behavior with a non-fatal failure, implying confidence that prompt retention is useful and low-risk. It assumes coding prompts belong to the same trust domain. That does not hold for Kivi, where application context may contain non-consenting third-party personal content that must never enter the write path (`../kivi-semantic-memory-position.md:106-125`).

3. **What privacy mechanism is enforceable: delimited redaction, semantic exclusion, or source separation?** Engram strips literal `<private>...</private>` regions before storing title/content (`internal/store/store.go:2916-2924`). This is hardcoded and syntactic; it assumes the producer marks private spans correctly. Kivi’s boundary is semantic and actor-relative, covering sensitive categories and third parties even without markup (`../kivi-semantic-memory-position.md:40-49,106-125`). Engram supplies precedent for pre-persistence enforcement, not for the classifier or audit proof Kivi needs.

4. **Must memory writes be complete, or may partial records enter and be repaired later?** Engram now rejects blank post-redaction titles and content because a poison mutation blocks the ordered project queue (`internal/store/store.go:2898-2929`). This is hardcoded at the shared store boundary, indicating high confidence learned from failure rather than original design. It assumes title/content are the minimum portable contract. Kivi’s minimum additionally includes type, tier, subject/provenance/status/evidence (`../kivi-semantic-memory-position.md:97-101`), so Engram’s validation boundary is structurally too weak.

### Representation and persistence

5. **Is a memory a typed document, a normalized claim graph, or an event/evidence structure?** Engram chooses a typed free-text document with metadata (`internal/store/store.go:118-137`). Type values are protocol conventions, not a closed database enum; relation type compatibility is explicitly not enforced (`internal/store/relations.go:28-31,77-100`). This is flexible but places semantic correctness in the agent. Kivi requires independent type and epistemic tier plus evidence-bearing sources (`../kivi-semantic-memory-position.md:66-102`); Engram’s schema conflates “observation” as record kind with the epistemic notion Kivi calls observed.

6. **Should changing knowledge update one stable topic, append a new claim, or create an explicit supersession edge?** A non-empty `topic_key` updates the most recently updated matching project/scope row in place and increments `revision_count`; distinct untitled saves append (`internal/store/store.go:2946-2990`). Separately, relations can record `supersedes` (`internal/store/relations.go:32-59`). This mixed answer is configurable only through caller-supplied topic keys, revealing moderate confidence in mechanism but low confidence in topic identity. Kivi requires superseded history to remain inspectable (`../kivi-semantic-memory-position.md:236-241`); in-place content replacement does not itself preserve old content, so only the relation route matches that requirement.

7. **Are scopes ownership/security boundaries or retrieval conveniences?** Engram stores `project`, `personal`, and `global`; project is the default, personal crosses projects when no override is supplied, and relations reject cross-project pairs (`docs/codebase/memory-core.md:43-49`; `internal/mcp/mcp.go:1123-1129`; `internal/store/relations.go:709-731`). Scope is partly configurable but ownership enforcement is hardcoded, showing high confidence after repeated contamination bugs. Kivi’s primary boundary is subject/consent rather than repository; project scope is useful precedent only for work-world partitioning, not non-retention of others.

8. **Should the local database or cloud be authoritative?** Engram chooses local SQLite; cloud is opt-in replication and shared access (`docs/codebase/mental-model.md:5-16`). This is architectural, not configurable once running. It assumes one user/device can operate offline and reconciliation cost is preferable to mandatory network latency. That assumption plausibly holds for a privacy-sensitive text client, but Kivi’s multi-surface transcript corpus may make provenance coordination harder (inference from `../kivi-semantic-memory-position.md:7,253-265`).

### Duplicate, conflict, and contradiction

9. **What counts as a duplicate: same semantic claim, same normalized body, same topic, or same external identity?** Engram uses three answers: exact normalized content plus project/scope/type/title within 15 minutes increments `duplicate_count`; equal `topic_key` revises a row; import dedupes by portable `sync_id` (`internal/store/store.go:2931-3038`; sync payload IDs at `internal/store/store.go:481-509`). The window is configurable in store config; topic and sync identity are caller-driven. This assumes near-time repeats are retries and topic keys are trustworthy. Kivi needs semantically equivalent observations across transcripts to accumulate evidence, where collapsing the rows may destroy source multiplicity (`../kivi-semantic-memory-position.md:82-100,247`).

10. **Does a conflict block the write, annotate it, or get resolved before persistence?** Engram commits the memory first, then runs non-fatal candidate detection; candidate failure never fails save (`internal/mcp/mcp.go:1408-1419,1449-1466`). Pending relation rows are inserted for later judgment (`internal/store/relations.go:350-357,454-489`). This hardcoded placement says availability of capture outranks consistency. Kivi says contradictions supersede and remain auditable (`../kivi-semantic-memory-position.md:238-241`), but leaves open whether an unresolved conflict may influence an answer; Engram offers precedent for “store first, reconcile later,” not evidence for safe disclosure.

11. **Who judges semantic relationships: deterministic code, an LLM, or a human?** Engram uses lexical FTS to propose candidates, then accepts agent/human-like `mem_judge` or optional semantic runner verdicts with actor/model/evidence/confidence provenance (`internal/store/relations.go:73-100,736-759`). This is pluggable at the judgment layer and deliberately avoids enforcing type compatibility (`internal/store/relations.go:28-31`). Kivi’s confirmation requirement is stricter: observed/hypothesized only become stated through an explicit user event (`../kivi-semantic-memory-position.md:95-101`), so model judgment cannot substitute for user confirmation.

12. **Should “not a conflict” be remembered?** Engram persists `not_conflict` as a real verdict so the same pair is suppressed later (`internal/store/relations.go:32-59,352-355`). This is hardcoded and signals high confidence, reinforced by a historical bug when it persisted nothing. Kivi likewise needs negative state for “not me anymore” and “forget” so rejected memories do not regrow (`../kivi-semantic-memory-position.md:238-242`), but Engram’s negative relation is pair-specific, not a suppression rule over future evidence.

### Retrieval and exposure

13. **Should retrieval be lexical, vector, structured, or hybrid?** Engram uses trigram FTS5 plus LIKE for short terms, with weighted BM25 and optional `all|any` token semantics (`internal/store/store.go:4162-4172,4246-4269`). This is hardcoded storage/search technology with only limits and candidate thresholds pluggable. It assumes code-memory vocabulary has strong lexical overlap. Kivi explicitly leaves retrieval mechanics open (`../kivi-semantic-memory-position.md:267-275`) and includes paraphrase, entity, temporal, and cross-transcript questions; the difference increases pressure toward structured or semantic recall without deciding which.

14. **How are results ordered?** Search orders by BM25 rank; title weight is 5, content 1, topic key 3, other indexed fields 0 (`internal/store/store.go:4246-4269`). Topic-key exact matches receive synthetic rank `-1000` and are prepended before truncation (`internal/store/store.go:4142-4152,4182-4213`). This is hardcoded and looks tuned rather than principled because no comment derives the weights. Kivi’s retrieval must also reason over tier, permission, recency/decay, evidence, and subject; Engram’s ordering contains none of those dimensions (inference from `../kivi-semantic-memory-position.md:78-100,153-177,238-242`).

15. **How much content should a first retrieval expose?** Engram returns bounded previews, with full content obtained separately; preview content is explicitly excluded from the struct and SQL truncates to 300 characters (`internal/store/store.go:168-170`; `internal/store/store.go:4240-4243`). This is hardcoded progressive disclosure optimized for agent token cost. Kivi’s Why panel requires enough source detail to explain use/withholding and abstention (`../kivi-semantic-memory-position.md:203-228`), so compact retrieval remains relevant but the caller-facing trace must be richer.

16. **Does permission govern retrieval or disclosure?** Engram has no epistemic permission dial; scope filters retrieval itself (`internal/mcp/mcp.go:1123-1140`). Kivi deliberately requires full retrieval followed by disclosure gating, with withheld items visible in the trace (`../kivi-semantic-memory-position.md:153-177`). This is a question Engram did not face, not a conflicting answer supported by evidence.

17. **What does the caller see on no match or partial failure?** `mem_search` returns a successful “No memories found” response; database search errors become tool errors suggesting simpler keywords; relation-annotation errors are silently ignored (`internal/mcp/mcp.go:1141-1160`). Save succeeds even if candidate detection or prompt capture fails (`internal/mcp/mcp.go:1421-1429,1449-1466`). This hardcodes graceful degradation and prioritizes availability. Kivi requires a reasoned abstention showing what was searched, so Engram’s empty result is precedent for non-fabrication but not for inspectable uncertainty (`../kivi-semantic-memory-position.md:203-228`).

### Change, deletion, ordering, and failure

18. **Does old knowledge expire, disappear from retrieval, or merely require review?** Engram sets review dates at 3 months for preferences, 6 for decisions, and 12 for policies; other types never decay, and review state is virtual rather than deletion (`internal/store/store.go:144-160,306-319`). This is hardcoded by type, suggesting an early guessed policy (“Phase 1”), not corpus-derived tuning. Kivi wants observations to lose standing and hypotheses to expire, while stated facts may remain; Engram’s type-based clock does not encode epistemic tier (`../kivi-semantic-memory-position.md:238-242,267-275`).

19. **What does delete mean?** Observations are soft-deleted by default; explicit hard delete exists, while session deletion is blocked if any observation—including soft-deleted—still references it (`docs/codebase/memory-core.md:48`; `internal/store/store.go:3535-3582`). This is deliberate audit/referential-integrity behavior with a compatibility escape hatch. Kivi distinguishes forget/demote/suppress/supersede, so one deleted timestamp cannot represent the user’s intended correction semantics (`../kivi-semantic-memory-position.md:236-248`).

20. **What ordering/idempotency is assumed?** MCP writes are serialized through one queue; started writes finish even if caller cancellation races, so outcome is deterministic (`internal/mcp/write_queue.go:40-88`). Sync is a per-target ordered mutation log with ACK and pull cursors (`internal/store/store.go:324-364`). Missing relation dependencies are ACKed into deferred storage so the cursor does not stall; invalid rows become dead and are not auto-retried (`internal/store/store.go:77-95`). This assumes entity mutations can be retried/idempotently applied and that availability requires advancing past bad records. Kivi must separately decide event ordering across transcript replay, corrections, confirmations, and reprocessing; Engram only solves storage/replication order.

21. **What happens under local write contention?** SQLite busy/locked writes retry after 10, 25, and 50 ms, and MCP admits at most 32 queued writes (`internal/store/store.go:42-51`; `internal/mcp/write_queue.go:12-35`). Queue overflow fails fast; reads do not wait behind the write worker (test contract at `internal/mcp/write_queue_test.go:63-195`). This hardcoded policy assumes low write concurrency and cheap client retries. A transcript extractor may burst many candidate/evidence writes, pushing Kivi away from that assumption without determining its alternative.

## 3. What the history says

### Reversals and rewrites

1. **Highest-value reversal: session-summary conflict adjudication was added, then removed.** PR [#847](https://github.com/Gentleman-Programming/engram/pull/847) made summaries surface conflict candidates; issue [#1016](https://github.com/Gentleman-Programming/engram/issues/1016) reported that this blocked session close; PR [#1023](https://github.com/Gentleman-Programming/engram/pull/1023) then skipped candidates for summaries. Current MCP save candidate detection remains post-commit and non-fatal (`internal/mcp/mcp.go:1449-1466`), while the repo guide still frames summaries as a save tool (`docs/codebase/memory-core.md:15-17`). The reversal says conflict review is valuable until it interferes with a terminal workflow; workflow completion won.

2. **Import changed from append/blind overwrite to identity dedupe plus last-write-wins.** Issue [#531](https://github.com/Gentleman-Programming/engram/issues/531) reported repeated import duplication, fixed by PR [#616](https://github.com/Gentleman-Programming/engram/pull/616). Issue [#244](https://github.com/Gentleman-Programming/engram/issues/244) asked to replace blind overwrite with LWW, implemented by PR [#917](https://github.com/Gentleman-Programming/engram/pull/917). Portable `sync_id` and updated/deleted timestamps are now part of observation payloads (`internal/store/store.go:481-499`). This is a rewrite driven by multi-writer history, not original intent.

3. **Project identity moved from live Git-derived naming to a persisted binding.** Issue [#739](https://github.com/Gentleman-Programming/engram/issues/739) showed origin rename/move silently forked memory; PR [#903](https://github.com/Gentleman-Programming/engram/pull/903) preserved identity across remote changes. Current detection initializes a private binding from origin/root and then reuses it (`internal/project/detect.go:122-146`). This abstraction was added because an inherited repository-name default stopped being stable.

4. **Search moved from default FTS ranking to weighted BM25, then from ordinary tokenization to trigram, then required batching after a regression.** Issue [#241](https://github.com/Gentleman-Programming/engram/issues/241) introduced weighted BM25; current weights are embedded in SQL (`internal/store/store.go:4246-4250`). Trigram indexing is now schema (`internal/store/store.go:2313-2335`), while issue [#955](https://github.com/Gentleman-Programming/engram/issues/955) reported ~2.5× conflict-scan regression and PR [#1017](https://github.com/Gentleman-Programming/engram/pull/1017) added page-batched ranking; the current code names that cause and fallback (`internal/store/relations.go:1405-1424`).

5. **Capture moved toward automation, then had to preserve the user-facing reply.** Issue [#547](https://github.com/Gentleman-Programming/engram/issues/547) added auto-save/passive-capture hooks. Issue [#584](https://github.com/Gentleman-Programming/engram/issues/584) found the memory protocol could replace the actual reply, fixed by PR [#1038](https://github.com/Gentleman-Programming/engram/pull/1038). Current agent guidance still makes capture a side effect around the main task (`docs/codebase/memory-core.md:7-23`). The recurring tension is memory completeness versus not hijacking the primary interaction.

### Recurring bug families

- **Missing/ambiguous identity:** mixed TEXT/BLOB project values hid 59% of a project ([#757](https://github.com/Gentleman-Programming/engram/issues/757)); NULL-project observations stranded topics and sync ([#758](https://github.com/Gentleman-Programming/engram/issues/758)); stale/open sessions made fallback ambiguous ([#1101](https://github.com/Gentleman-Programming/engram/issues/1101)). Current code centralizes project normalization and refuses ambiguous cross-ownership (`internal/store/store.go:2912-2945`; active-session limitations are admitted at `internal/store/store.go:2700-2710`).
- **One bad ordered mutation stalls unrelated work:** blank title/content poisoned queues ([#695](https://github.com/Gentleman-Programming/engram/issues/695), [#686](https://github.com/Gentleman-Programming/engram/issues/686)); missing dependencies stalled imports ([#649](https://github.com/Gentleman-Programming/engram/issues/649), [#671](https://github.com/Gentleman-Programming/engram/issues/671)). Current validation explains the head-of-line risk (`internal/store/store.go:2898-2904`), and deferred/dead states allow cursor advance (`internal/store/store.go:77-95`).
- **Search correctness and scale:** language mismatch returned zero results ([#720](https://github.com/Gentleman-Programming/engram/issues/720)); broad `any` queries ran for minutes ([#662](https://github.com/Gentleman-Programming/engram/issues/662)); quote escaping crashed FTS ([#664](https://github.com/Gentleman-Programming/engram/issues/664)); 5k scans hung ([#721](https://github.com/Gentleman-Programming/engram/issues/721)). Current search still remains lexical and advises simpler keywords on failure (`internal/mcp/mcp.go:1134-1147`).
- **Sync completeness:** relations were omitted from local chunks ([#353](https://github.com/Gentleman-Programming/engram/issues/353)); relation mutations lacked backfill ([#496](https://github.com/Gentleman-Programming/engram/issues/496)); deletes were materialized as upserts or dropped ([#785](https://github.com/Gentleman-Programming/engram/issues/785), [#837](https://github.com/Gentleman-Programming/engram/issues/837)). The present wire model carries explicit op/delete fields (`internal/store/store.go:298-303,468-509`).

### Shortcuts and compatibility debt

- `sessions.project` is declared non-null only for newly created tables; old databases retain NULL because `CREATE TABLE IF NOT EXISTS` does not rewrite them, so readers use `ifnull` and repair paths instead of a full table migration (`internal/store/store.go:3549-3553`). This is backwards compatibility, not deliberate domain modeling.
- Relation type compatibility is reserved but unenforced; the agent judges it (`internal/store/relations.go:28-31,83-84`). This is explicit incomplete work.
- Candidate detection errors are swallowed to protect save availability (`internal/store/relations.go:350-357`; `internal/mcp/mcp.go:1449-1466`). This is deliberate graceful degradation, not an accident, but it creates silent inconsistency.
- The active-session resolver admits that liveness is unobservable because sessions carry no PID/heartbeat; it substitutes recent recorded work (`internal/store/store.go:2700-2710`). This is an admitted approximation.
- The cloud runtime preserves legacy environment credentials alongside managed principals and special-cases auth order for compatibility (`cmd/engram/cloud.go:141-152`). This is compatibility debt, not evidence that dual auth models are desirable.
- A CLI conflict “show” path still lists all relations and scans for an ID, with a comment to add direct lookup (`cmd/engram/conflicts.go:190-191`). This is an admitted shortcut outside the semantic core.

## 4. Unexamined defaults

1. **Free-form `type` strings.** No database enum or type/tier cross-product exists (`internal/store/store.go:118-137`). An untried alternative in this repo is a versioned closed schema with explicit unknown handling. There is no comment/test showing deliberation over that choice.
2. **One observation has one session source.** `session_id` is singular while evidence is not a first-class table (`internal/store/store.go:118-137`). An untried alternative is many-to-many evidence edges, required by Kivi’s multi-transcript observations (`../kivi-semantic-memory-position.md:82-100,283`).
3. **Wall-clock timestamps as ordering truth.** Updates, dedupe, topic choice, and LWW use timestamps (`internal/store/store.go:2955-2971,2996-3017`). An untried alternative is logical/version-vector ordering. The repo’s sync bugs show ordering mattered, but no core comment justifies trusting clock order.
4. **Latest topic row wins.** If historical duplicates share a topic key, the most recently updated/created row is revised (`internal/store/store.go:2947-2958`). An untried alternative is rejecting ambiguous topic identity. No test/comment appears to deliberate that ambiguity.
5. **Project and scope stand in for subject/tenant.** Relations are guarded by project equality (`internal/store/relations.go:709-731`). An untried alternative is explicit `subject_id` plus consent boundary; Engram’s coding-agent setting did not require it.
6. **Syntactic private tags are trusted.** Redaction is producer-authored markup (`internal/store/store.go:2916-2924`). An untried alternative is a pre-write classifier plus logged exclusion reason, which Kivi explicitly demands (`../kivi-semantic-memory-position.md:45-49`).
7. **Trigram lexical overlap is the recall primitive.** Both indexes hardcode trigram (`internal/store/store.go:2313-2335`). Alternatives—word tokenization, embeddings, entity/time indices, hybrid fusion—are absent from production, though Kivi intentionally leaves the choice open (`../kivi-semantic-memory-position.md:267-275`).
8. **Confidence defaults to certainty.** The tool describes 1.0 as default while accepting 0..1 (`internal/mcp/mcp.go:955`; `internal/store/relations.go:66-69`). An untried alternative is “unknown unless supplied.” No rationale is present.
9. **Failure to annotate relations is invisible to the caller.** Relation-load failure falls back to an empty map (`internal/mcp/mcp.go:1150-1160`). An untried alternative is a partial-result envelope naming missing annotations. This conflicts with Kivi’s inspectability goals but is not tested as a product decision.
10. **Other memory types never age.** Only decision/policy/preference receive `review_after` (`internal/store/store.go:306-319`). An untried alternative is tier/evidence-dependent decay. The “Phase 1” comment marks incompleteness, not confidence.

## 5. Questions this repo never faced

These derive from Kivi’s position, not from missing Engram features.

- **Who is the subject of each candidate, and how is “the user” distinguished from a person merely present in application context?** Kivi makes non-retention actor-relative (`../kivi-semantic-memory-position.md:106-125`); Engram records project ownership, not human subject (`internal/store/store.go:118-137`).
- **How is an exclusion decision proven without retaining the excluded content?** Kivi requires a count/reason visible in an extraction log (`../kivi-semantic-memory-position.md:45-49,121-125`); Engram has only destructive private-tag stripping and no drop record (`internal/store/store.go:2916-2924`).
- **Can sensitive-category classification itself leak the fact it classified?** Kivi wants exclusion reasons but also non-retention (`../kivi-semantic-memory-position.md:45-49`); Engram has no analogous audit/privacy tradeoff.
- **How are type and epistemic tier kept independent through extraction, retrieval, disclosure, editing, and sync?** Kivi requires both axes (`../kivi-semantic-memory-position.md:66-102`); Engram has one free-form type and relation confidence (`internal/store/store.go:118-137`; `internal/store/relations.go:66-69`).
- **What exact event counts as user confirmation, and can a later correction revoke it?** Kivi requires an explicit timestamped confirmation (`../kivi-semantic-memory-position.md:95-101`); Engram’s relation judgments can be system-authored (`internal/store/relations.go:736-746`).
- **How can “forget” and “not me anymore” prevent re-derivation while retaining enough suppression state to honor the request?** Kivi explicitly identifies deletion alone as insufficient (`../kivi-semantic-memory-position.md:238-248`); Engram’s soft delete/tombstone prevents replica resurrection, not semantic re-extraction (`docs/codebase/memory-core.md:48`).
- **How is a hypothesis stored grammatically as a question and prevented from entering action planning?** Kivi treats that grammar as an enforcement mechanism (`../kivi-semantic-memory-position.md:93-95`); Engram content is unrestricted text (`internal/store/store.go:118-137`).
- **How does the permission dial filter disclosure after full retrieval while still showing withheld-count traces?** Kivi requires this exact separation (`../kivi-semantic-memory-position.md:153-177`); Engram filters at query time (`internal/mcp/mcp.go:1123-1140`).
- **How can regular dictation be structurally unable to access observation/hypothesis stores while Hey Kivi can?** Kivi requires separate retrieval paths (`../kivi-semantic-memory-position.md:181-199`); Engram exposes one core through several interfaces (`docs/codebase/interfaces.md:3-5`).
- **How is an abstention evaluated as a retrieved-evidence trace rather than an empty search?** Kivi requires showing what was searched (`../kivi-semantic-memory-position.md:203-228`); Engram returns only “No memories found” (`internal/mcp/mcp.go:1145-1147`).
- **How is confirmation attention budgeted per user/week and prioritized by value?** Kivi leaves the budget number open but commits to rationing (`../kivi-semantic-memory-position.md:218-223,267-275`); Engram has no attention-cost model.
- **How are time-relative episodes represented when transcripts say “Thursday,” “next week,” or revise a date?** Kivi’s examples depend on temporal normalization (`../kivi-semantic-memory-position.md:74-76,118-123`); Engram stores free text plus record timestamps (`internal/store/store.go:118-137`).
- **What provenance is shown when a belief is assembled from many transcripts, and what happens when one source is deleted?** Kivi requires source arrays and tap-through provenance (`../kivi-semantic-memory-position.md:97-101,236-247`); Engram has a single session ID and relation orphaning semantics, not evidence recomputation (`internal/store/store.go:118-137`; `internal/store/relations.go:42-48`).

## 6. What the tests do not cover

1. A different sensitive-topic or third-party retention policy would pass because no schema field or test models subject consent; private-tag tests can only distinguish marked from unmarked spans (`internal/store/store.go:2916-2924`).
2. A system that silently treats observed patterns as stated facts would pass because tier and confirmation events do not exist (`internal/store/store.go:118-137`).
3. A system that retrieves only permitted tiers instead of retrieving all and withholding at disclosure would pass because Engram has no disclosure layer (`internal/mcp/mcp.go:1123-1140`).
4. A system that hallucinates after an empty search is outside Engram’s boundary; tests stop at the tool response, which is merely “No memories found” (`internal/mcp/mcp.go:1141-1147`).
5. Different BM25 weights, exact-topic sentinel rank, top-k, and decay months would preserve most correctness tests; tests prove bounds/determinism, not that these values maximize user recall or trust (`internal/store/store.go:306-319,4142-4152,4246-4269`; `internal/store/relations_bm25_test.go:9-56`).
6. Exact-window dedupe could merge two distinct repeated statements and still pass because tests assert mechanical equality/window behavior, not semantic identity (`internal/store/store.go:2996-3028`).
7. Topic upsert could overwrite a genuine historical change and still pass because the contract expects one latest row; no test can recover the overwritten content from the observation table (`internal/store/store.go:2947-2990`).
8. A wrong but well-formed semantic verdict can pass: tests validate vocabulary, range, provenance, idempotency, and project guard—not truth (`internal/store/judge_by_semantic_test.go:82-204,238-439`).
9. A stale memory may remain active for any unlisted type and pass because only three type strings get review clocks (`internal/store/store.go:306-319`).
10. Relation annotation can fail and search still succeeds by design, so tests establish availability rather than caller awareness of incomplete conflict context (`internal/mcp/mcp.go:1150-1160`).
11. LWW can select the semantically wrong writer under clock skew and still pass if timestamp ordering is internally consistent (`internal/store/store.go:481-499`; LWW rewrite is historical PR #917). The suite tests deterministic application, not real clock validity.
12. Replaying the same transcript after “forget” can regenerate the same semantic candidate and still pass because tombstones key stored entities/sync IDs, not derivation predicates (`internal/store/store.go:1000-1009,501-509`).
13. Search in another language can remain poor while FTS correctness tests pass; issue [#720](https://github.com/Gentleman-Programming/engram/issues/720) is direct evidence that lexical test fixtures did not distinguish this answer. Current indexes remain trigram lexical (`internal/store/store.go:2313-2335`).
14. The Why panel, withheld trace, source attribution UX, inline correction, confirmation budget, and dictation/Hey Kivi structural split have no Engram tests because they have no corresponding Engram model or execution path (`../kivi-semantic-memory-position.md:173-177,181-228,244-249`; contrast `docs/codebase/interfaces.md:3-5`). On those points Engram offers no precedent at all.

## Bottom line of the map

Engram is strongest evidence for operational memory mechanics: local-first persistence, explicit identity, bounded progressive retrieval, post-save conflict annotation, negative conflict judgments, soft deletion, mutation journaling, dependency deferral, and the fact that compatibility/multi-writer behavior becomes the dominant complexity (`docs/codebase/mental-model.md:29-59`; `internal/store/store.go:77-95,283-319`; `internal/store/relations.go:350-357`). It is weak evidence for Kivi’s defining decisions because it delegates admission to an agent and lacks subject consent, epistemic tiers, multi-source provenance, disclosure permissions, abstention traces, and re-derivation suppression (`internal/store/store.go:118-137`; Kivi commitments at `../kivi-semantic-memory-position.md:277-287`).

The most valuable historical signal is reversal: features that looked locally correct—summary conflict review, Git-derived project identity, blind import, unbounded scans, automatic capture—failed when they crossed workflow, identity, scale, or user-attention boundaries. The code now embodies those repairs, but the repairs are evidence about the questions, not proof that their current answers transfer to Kivi.
