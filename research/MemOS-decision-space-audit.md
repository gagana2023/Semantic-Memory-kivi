## Orientation

### Core logic versus glue

There are two core answers, not one.

1. The Python product core is `MOSCore` plus `GeneralMemCube`, `MemReader`, textual memory managers, scheduler, and graph/vector stores. `MOSCore.add` sends content through a reader and cube; `MOSCore.search` selects accessible cubes and invokes the configured textual memory; the API routers/handlers normalize requests around that (`src/memos/mem_os/core.py:295-411`, `src/memos/mem_os/core.py:669-782`; `src/memos/mem_cube/general.py:23-67`). Factories, API clients, provider-specific LLM/embedder/DB classes, examples, deployment, and MCP are adapters/glue.
2. The TypeScript local core is a more opinionated pipeline: capture → task boundary classification → semantic chunking → summarization → exact and semantic dedup/update → SQLite + embedding → hybrid recall → prompt/tool exposure (`packages/memos-core/src/ingest/task-processor.ts:30-466`; `packages/memos-core/src/ingest/worker.ts:10-299`; `packages/memos-core/src/recall/engine.ts:31-255`). Its OpenClaw hooks, bridge, viewer, Hub client/server, and adapters are integration layers.

This split is deliberate at the repository level but the relationship between the two semantic models is unclear: they do not share a canonical memory schema. The public TypeScript schema describes events/hits, while the Python system uses Pydantic memory items and backend-specific persistence (`packages/memos-schema/src/index.ts:30-87`; `src/memos/mem_reader/memory.py:1-96`).

### Data model

The TypeScript write contract accepts an event containing ordered role/content messages plus app/agent/user/workspace/session identity, tags, cwd, and arbitrary source (`packages/memos-schema/src/index.ts:3-42`). Internally each message becomes a `Chunk` with session, turn, sequence, role, raw content, summary, owner, dedup state/target/reason, merge count/history, timestamps, and optional task/skill links (`packages/memos-core/src/types.ts:17-40`). SQLite stores raw content and summary in `chunks`, maintains trigram FTS through triggers, and stores vectors separately as dimensioned blobs keyed by chunk ID (`packages/memos-core/src/storage/sqlite.ts:23-75`). Tasks are mutable episode-like groupings with `active|completed|skipped` state (`packages/memos-core/src/types.ts:44-56`; `packages/memos-core/src/storage/sqlite.ts:85-96`).

Migration is code-driven and additive rather than version-file-driven: startup calls a fixed sequence of migration methods and many methods probe columns then `ALTER TABLE` (`packages/memos-core/src/storage/sqlite.ts:99-123`, `packages/memos-core/src/storage/sqlite.ts:130-214`). The serialized merge history is JSON text, not a normalized relation (`packages/memos-core/src/types.ts:35-37`; `packages/memos-core/src/storage/sqlite.ts:605-607`). Exact idempotency uses a 16-hex-character prefix of SHA-256 content (`packages/memos-core/src/storage/sqlite.ts:3355-3357`).

The Python model is richer in memory categories but looser in invariants. The simple reader produces `LongTermMemory` or `UserMemory`, attaching sources and contextual metadata, and normalizes unknown LLM-produced types back to `LongTermMemory` (`src/memos/mem_reader/simple_struct.py:105-155`, `src/memos/mem_reader/simple_struct.py:448-467`). API retrieval recognizes working, long-term, user, outer, tool, skill, and preference memories (`src/memos/api/handlers/memory_handler.py:222-291`). This taxonomy does not encode Kivi’s independent `type × tier` model; that mismatch is direct, not inferred (`../kivi-semantic-memory-position.md:69-95`).

### Main execution path: entry to persistence

Python API: `POST /product/add` is validated/normalized by Pydantic request models, dispatched through handlers/MOS, parsed by the selected reader into textual items, optionally scheduled for fine extraction, then written by the selected textual memory into a graph/vector backend (`src/memos/api/product_models.py:679-824`; `src/memos/mem_os/core.py:669-782`; `src/memos/mem_reader/simple_struct.py:369-467`; `src/memos/memories/textual/general.py:82-169`). The scheduler introduces asynchronous fast/fine transfer and version/log persistence; failures in fine transfer are specifically prevented from deleting the fast memory (`tests/mem_scheduler/test_mem_read_handler_fast_cleanup.py:71-102`).

TypeScript local: captured `ConversationMessage`s enter `IngestWorker`; task processing classifies boundaries and may finalize/start tasks, content is chunked, summarized/embedded, checked first by exact content hash and then against the top five semantically similar chunks, optionally judged as `DUPLICATE`, `UPDATE`, or `NEW`, and finally inserted with dedup history plus an embedding if active (`packages/memos-core/src/ingest/worker.ts:64-108`, `packages/memos-core/src/ingest/worker.ts:129-299`). Recall embeds the query, runs local FTS and vector retrieval plus short-term pattern and optional Hub retrieval, fuses ranked lists, applies MMR and recency, filters relative to the top score, and exposes summary/excerpt plus source reference (`packages/memos-core/src/recall/engine.ts:31-127`, `packages/memos-core/src/recall/engine.ts:132-255`).

### Config surface

The TypeScript core’s complete semantic-memory config is: summarizer provider/endpoint/key/model/headers/timeout/temperature; embedding provider/endpoint/key/model/headers/timeout/batch size/dimensions/retry; DB path; recall default/max result counts, default/floor score, RRF constant, MMR lambda, recency half-life, vector scan cap; semantic-dedup threshold; evidence wrapper tag; task auto-finalization; and skill/sharing/telemetry settings (`packages/memos-core/src/types.ts:172-192`, `packages/memos-core/src/types.ts:248-327`). Defaults are centralized (`packages/memos-core/src/types.ts:331-363`) and environment substitution accepts `${UPPER_CASE_NAME}` in string values, replacing missing variables with the empty string (`packages/memos-core/src/config.ts:4-8`).

The Python surface is much larger and distributed. Pydantic configuration covers chunkers, embedders, LLMs, memories, graph/vector DBs, readers, schedulers, chat, users, feedback, parsers, rerankers, and cubes (`src/memos/configs/base.py:15-68`; `src/memos/configs/chunker.py:8-48`; `src/memos/configs/memory.py:1-260`; `src/memos/configs/mem_scheduler.py:25-139`). API/environment switches include chat enablement, scheduler enablement, embedding inclusion, internet enablement, auth, rate limiting, CORS, graph backend, and Dream/MMR recall hooks (`src/memos/api/routers/server_router.py:91`; `src/memos/api/handlers/component_init.py:245-311`; `src/memos/api/server_api_ext.py:80-127`; `src/memos/api/handlers/search_handler.py:32-40`). Provider credentials/model env vars are constructed by provider-specific configuration; scheduler model fallback is explicitly separate from the chat model (`src/memos/configs/mem_scheduler.py:211-231`; `tests/mem_scheduler/test_config.py:204-238`).

### What tests exercise

The Python tests exercise initialization and delegation with mocks; simple-reader parsing and unparseable-LLM fallback; source-role filtering for preference extraction; basic textual add/update/search/delete; tree merge/path reuse; hybrid graph/vector merging; scheduler queue/config/version mechanics; API shape and backward-compatibility normalization; delete-mode exclusivity; MMR candidate pruning; and select failure fallbacks (`tests/mem_os/test_memos_core.py:157-796`; `tests/mem_reader/test_simple_structure.py:38-160`; `tests/mem_reader/test_source_filter.py:51-145`; `tests/memories/textual/test_general.py:79-337`; `tests/memories/textual/test_tree_manager.py:54-143`; `tests/memories/textual/test_tree_retriever.py:27-160`; `tests/api/test_memory_handler_delete.py:14-145`). Many are mock interaction tests rather than end-to-end semantic-quality tests; this is an inference from their fixtures and assertions (`tests/memories/textual/test_general.py:19-77`; `tests/mem_os/test_memos_core.py:18-155`).

The standalone `packages/memos-core` directory has no colocated `*.test.ts`/`*.spec.ts` files in this checkout. That does not prove no TypeScript behavior is tested elsewhere, but it means the core package itself supplies no immediately traceable executable evidence for its thresholds or combined pipeline.

## 1. Decision inventory

Each item begins with the recoverable question.

### What enters memory?

**Should memory ingest every conversational role, only user-authored statements, or a separately classified subset?** TypeScript accepts `user|assistant|tool|system` and stores role on every chunk (`packages/memos-core/src/types.ts:3-13`, `packages/memos-core/src/types.ts:19-39`). Placement: hardcoded union, with no semantic-retention policy plug-in. This assumes all host-visible text is eligible evidence and role is sufficient downstream context. For Kivi this assumption does not hold: third-party and sensitive content must be barred before storage, and ordinary dictation has a structurally restricted memory path (`../kivi-semantic-memory-position.md:21-25`, `../kivi-semantic-memory-position.md:47`, `../kivi-semantic-memory-position.md:181-199`). The difference pushes the decision upstream of MemOS’s chunk/storage boundary.

**Should extraction preserve unsupported/ambiguous input or discard it?** The TypeScript task processor has trivial-pattern and minimum-length gates; the Python simple reader falls back to a node when fine extraction is unparseable (`packages/memos-core/src/ingest/task-processor.ts:7-18`, `packages/memos-core/src/ingest/task-processor.ts:410-466`; `src/memos/mem_reader/simple_struct.py:411-467`; `tests/mem_reader/test_simple_structure.py:150-160`). Placement: hardcoded heuristics in TypeScript; deliberate tested availability fallback in Python. It assumes losing short acknowledgements is cheap and losing the entire input on an LLM format failure is expensive. Kivi’s requirement to log dropped candidates makes silent length/triviality drops insufficient; the direction is toward reason-bearing rejection rather than generic fallback (`../kivi-semantic-memory-position.md:47-51`).

**Should assistant/tool material be evidence for preferences?** Python now removes assistant/tool/polluted sources before preference extraction (`src/memos/mem_reader/source_filter.py:26-43`, `src/memos/mem_reader/source_filter.py:122-183`; `tests/mem_reader/test_source_filter.py:51-145`). Placement: hardcoded policy object and tested; history says it was added as a fix, not present from first principles (`9160632f`, “filter polluted sources before preference extraction”). It assumes preferences should be attributable to the user, but it applies only to preference extraction. Kivi extends that ownership barrier to every retained belief and to third-party personal content, so the difference widens the policy’s scope.

### Representation and storage

**Should the atomic unit be a raw event, extracted proposition, semantic chunk, entity/relation, or episode?** TypeScript stores paragraph chunks and mutable tasks; `ChunkKind` has only `paragraph` (`packages/memos-core/src/types.ts:19-58`). Python stores typed memory nodes and optional tree relations (`src/memos/mem_reader/simple_struct.py:369-467`; `src/memos/api/handlers/memory_handler.py:222-291`). Placement: hardcoded in TypeScript, pluggable memory backend/taxonomy in Python. The two answers reveal low repository-wide confidence. Kivi requires entity/preference/episode orthogonal to stated/observed/hypothesised; neither representation carries that invariant (`../kivi-semantic-memory-position.md:69-95`).

**Should raw evidence and derived summaries both persist?** TypeScript stores `content` and `summary`, and returns a source reference with timestamp, role, and session (`packages/memos-core/src/storage/sqlite.ts:23-34`; `packages/memos-core/src/types.ts:71-85`). Placement: hardcoded schema, suggesting high confidence. It assumes retaining full source text is acceptable. Kivi agrees on attribution but not blanket retention: third-party content may be used transiently and then must not persist (`../kivi-semantic-memory-position.md:21-25`, `../kivi-semantic-memory-position.md:227`). The difference separates “provenance pointer” from “retained raw payload.”

**Should vectors live beside records, in a vector service, or be recomputable cache?** TypeScript stores dimensioned BLOBs in SQLite, deletes them by foreign-key cascade, and has no model/provider identity in the row (`packages/memos-core/src/storage/sqlite.ts:70-75`). Python makes vector/graph backends pluggable (`src/memos/vec_dbs/factory.py:1-31`; `src/memos/graph_dbs/factory.py:1-44`). Placement: hardcoded local versus pluggable server architecture. The local answer assumes one embedding space per database. Issue #1333 demonstrates that assumption breaks on model changes and silently degrades vector recall.^1 Kivi has left storage mechanics open, so this is precedent about migration identity, not evidence for a backend (`../kivi-semantic-memory-position.md:267-275`).

**Should schema evolution be explicit/versioned or opportunistic at startup?** TypeScript performs ordered, catch-tolerant column probes and additive alterations (`packages/memos-core/src/storage/sqlite.ts:99-123`, `packages/memos-core/src/storage/sqlite.ts:130-214`). Placement: hardcoded startup migration. It assumes a single-process local database and that “table may not exist” is an acceptable reason to swallow migration errors. For Kivi’s user-visible reversibility/auditability, the unresolved question is whether memory-history correctness can tolerate ambiguous migration completion; MemOS provides no evidence.

### What is discarded?

**Should short or trivial utterances be permanently dropped, stored raw but not indexed, or retained as episode context?** TypeScript drops/marks trivial content through fixed patterns and language-dependent length checks (`packages/memos-core/src/ingest/task-processor.ts:7-18`, `packages/memos-core/src/ingest/task-processor.ts:410-466`). Placement: hardcoded, indicating convenience rather than a stable public contract. It assumes semantic density tracks characters and acknowledgements have no future evidentiary role. Kivi may need “transcripts that produce nothing” for evaluation, but also proof of why nothing was retained (`../kivi-semantic-memory-position.md:261-264`, `../kivi-semantic-memory-position.md:279-287`).

**Should inactive duplicates be deleted or retained with lineage?** TypeScript marks old chunks `duplicate`/`merged`, keeps targets/reasons/history, and retrieves only active material (`packages/memos-core/src/ingest/worker.ts:198-253`; `packages/memos-core/src/storage/sqlite.ts:631-634`). Placement: hardcoded workflow with visible viewer states, suggesting deliberate auditability. It assumes append-plus-retire storage cost is acceptable. Kivi’s supersession requirement aligns structurally, but Kivi distinguishes user correction/demotion/suppression from model-judged semantic duplication (`../kivi-semantic-memory-position.md:239-248`).

### Duplicate, contradiction, and conflict

**Should identical replay update recency/evidence, be ignored, or create a new observation?** TypeScript exact-hash handling retires/replaces through merge history; semantic candidates above `0.80` go to an LLM judge (`packages/memos-core/src/ingest/worker.ts:151-182`, `packages/memos-core/src/ingest/worker.ts:196-258`). The hash is truncated SHA-256 (`packages/memos-core/src/storage/sqlite.ts:3355-3357`). Placement: exact behavior hardcoded; similarity threshold configurable. This assumes repetition is primarily transport duplication, not evidence count. Kivi treats repeated observations as evidence but forbids automatic promotion (`../kivi-semantic-memory-position.md:88-95`); therefore idempotency identity must be separable from semantic repetition.

**When a new statement changes an old one, should the system merge text, supersede the old record, retain both, or ask?** The LLM returns `DUPLICATE|UPDATE|NEW`; `UPDATE` creates a new active chunk with merged summary and retires the target, while recording prior/new summaries (`packages/memos-core/src/ingest/worker.ts:196-253`). Placement: LLM-pluggable judgment wrapped in hardcoded state transition. It assumes the model can distinguish elaboration from contradiction and that a merged summary preserves truth. Kivi requires contradiction to supersede, explicit user promotion for tier changes, and source-level attribution. The difference pushes toward typed conflict events and against unqualified summary fusion (`../kivi-semantic-memory-position.md:95`, `../kivi-semantic-memory-position.md:239-248`).

**Should conflict resolution be synchronous on write or asynchronous/versioned?** Python added scheduler version control and conflict-aware work later (`tests/mem_scheduler/test_version_control.py:51-250`), while issue #948 states the system previously lacked conflict-aware updates, causing duplicates and newer memories not to take effect.^2 Placement: later abstraction, evidence that the original append/update answer stopped working. Kivi’s correction semantics make this load-bearing rather than optional.

### Retrieval and ordering

**Should retrieval be lexical, vector, graph, or hybrid?** TypeScript runs FTS, vector, pattern, and optional Hub sources, then reciprocal-rank fusion (`packages/memos-core/src/recall/engine.ts:42-127`; `packages/memos-core/src/recall/rrf.ts:1-45`). Python exposes embedding/full-text modes and tree graph/vector merging (`src/memos/api/product_models.py:43-49`; `tests/memories/textual/test_tree_retriever.py:45-160`). Placement: hybrid hardcoded locally, pluggable/mode-selectable in Python. This assumes recall quality benefits from source diversity enough to pay extra latency. Kivi leaves mechanics open; the relevant Kivi distinction is that disclosure happens after retrieval and depends on permission, which MemOS’s score pipeline does not encode (`../kivi-semantic-memory-position.md:21`, `../kivi-semantic-memory-position.md:131-179`).

**Should ranking optimize relevance alone, relevance plus diversity, or relevance plus time?** TypeScript fuses ranks, MMR-reranks at lambda `0.7`, applies a 14-day exponential half-life with a `0.3` floor multiplier, and then threshold-filters (`packages/memos-core/src/recall/engine.ts:132-176`; `packages/memos-core/src/recall/mmr.ts:4-58`; `packages/memos-core/src/recall/recency.ts:1-25`). Placement: lambda/half-life configurable, decay floor hardcoded. This assumes freshness and diversity apply uniformly across all memory kinds. Kivi explicitly decays observations but does not say stated facts or episodes decay in the same way (`../kivi-semantic-memory-position.md:239-242`); MemOS’s global decay therefore answers a different question.

**Should low absolute scores be compared to a global cutoff or to the best result in the current query?** TypeScript uses `topScore × minScore × 0.3`, then normalizes (`packages/memos-core/src/recall/engine.ts:169-176`). Placement: `minScore` configurable but the relative formula and `0.3` are hardcoded. It assumes at least one candidate supplies a trustworthy local scale. On an all-bad candidate set, relative filtering can still admit bad results; Kivi requires abstention with an explanation (`../kivi-semantic-memory-position.md:227-230`, `../kivi-semantic-memory-position.md:284-285`).

**Should session identity be a hard filter, a soft feature, or merely provenance?** TypeScript query schemas accept optional session/workspace/user/agent identity, while cross-session recall can be enabled by host integration (`packages/memos-schema/src/index.ts:46-55`). Issue #1532 reports agents acting on cross-session context as if current, leading to a subsequent fix.^3 Placement: adapter behavior, historically unstable. Kivi’s source display and disclosure modes make session provenance caller-visible, not just a search filter (`../kivi-semantic-memory-position.md:227`).

### Caller exposure, failure, and confidence

**Should the caller receive raw evidence, summaries, scores, provenance, or only injected prose?** TypeScript search exposes summary, excerpt, score, task/skill IDs, owner/origin, and source timestamp/role/session; prompt injection collapses hits into a formatted section (`packages/memos-core/src/types.ts:71-105`; `packages/memos-schema/src/index.ts:90-97`). Placement: hardcoded contract. It assumes technical provenance is enough explanation. Kivi requires retrieved/withheld/used distinctions and human-legible reasons, including abstentions (`../kivi-semantic-memory-position.md:227-230`).

**If summarization, embedding, or dedup fails, should ingestion fail closed, fail open, preserve raw memory, or report partial success?** The worker counts errors and continues per message; merge re-embedding failure is logged and processing continues (`packages/memos-core/src/ingest/worker.ts:64-108`, `packages/memos-core/src/ingest/worker.ts:217-232`). Python preserves fast memories if async fine extraction fails (`tests/mem_scheduler/test_mem_read_handler_fast_cleanup.py:71-102`). Issue #1303 shows import once reported success despite failed summarization/dedup/embedding steps, motivating explicit step-failure reporting.^4 Placement: deliberate availability bias added after failure reports. Kivi’s exclusion barrier cannot fail open without violating a product claim; MemOS does not face that failure cost.

**Should low-confidence classification retry, abstain, or accept first pass?** Task boundaries below `0.65` confidence receive a second arbitration pass (`packages/memos-core/src/ingest/task-processor.ts:196-216`). Placement: hardcoded threshold and procedure. It assumes a second LLM judgment is worth cost/latency only for “NEW” boundaries. Kivi’s epistemic confidence applies to stored belief tiers, not merely episode segmentation, so this precedent is not evidence for promotion.

### Change over time, idempotency, and ordering

**Should time affect record truth, retrieval priority, or both?** TypeScript preserves created/updated timestamps, task boundaries, merge history, and applies retrieval decay (`packages/memos-core/src/types.ts:35-39`; `packages/memos-core/src/recall/recency.ts:12-25`). It does not encode belief validity intervals. Kivi requires `first_seen_at`, `last_confirmed_at`, evidence count, status, suppression, and expiration by tier (`../kivi-semantic-memory-position.md:88-101`, `../kivi-semantic-memory-position.md:239-248`). The difference pushes from ranking-time freshness to state-transition time.

**What ordering is assumed?** Messages carry timestamp, turn ID, session key, and `seq`; SQLite indexes `(session_key, turn_id, seq)` and `(session_key, created_at, seq)` (`packages/memos-core/src/types.ts:5-13`; `packages/memos-core/src/storage/sqlite.ts:36-43`). Placement: hardcoded schema. It assumes host ordering is trustworthy and a sequence is scoped within a turn/session. There is no explicit late-arrival or clock-skew policy: unclear. Kivi’s contradiction and distributed-transcript evidence questions make out-of-order arrival observable, but its position document does not yet decide it.

**What is idempotent?** Exact content hash within the TypeScript local store is treated as duplicate, but public `MemoryEvent` has no caller-supplied idempotency key (`packages/memos-schema/src/index.ts:30-42`; `packages/memos-core/src/storage/sqlite.ts:487-492`). Issue #2141 reports a replay loop producing 6,076 writes, about 90% duplicates, and argues for server-side windowed dedup.^5 This is a recurring bug class, not merely theoretical. Kivi must distinguish delivery retry, repeated evidence, and genuinely restated fact; MemOS does not encode those as separate identities.

## 3. What the history says

Reversals are the highest-value signal because they show a once-defensible answer failed under real constraints.

- **Highest-value reversal — prompt injection lifecycle:** memory injection moved from `before_agent_start` to `before_prompt_build` (`e3f4e51e`), a context-engine registration was added (`b812c47d`), then explicitly reverted to `before_prompt_build` (`9c1e492d`). Another commit says “revert move memory to system prompt” (`5eb27d53`). The repo repeatedly changed *where recalled memory enters agent context*, indicating this is not settled glue. Issue #1532 supplies the failure mode: cross-session memory can look like current instruction and trigger action.^3
- **Highest-value reversal — reflection scoring:** “chunk batch reflection scoring” shipped and was reverted two days later (`21a27ed1`, `6734a0ea`). The commit title does not state why; intent is unclear without accessible PR discussion. It is still valuable evidence that an added confidence/evaluation stage had unacceptable effects.
- **Retrieval ranking reversals:** history records “unuse rerank,” then “backtrack knowledge retrieval,” then “use knowledge embedding score rerank” (`1b853e14`, `893a593b`, `0a9398d5`). Later MMR dedup was added (`6e5e2c4a`). This is repeated rewriting of the ordering answer, not a stable algorithmic precedent.
- **Concurrency reversal:** pool optimization was reverted (`d42a7ced`). Issue #1273 later reported request-scoped thread pools leaking to 8,744 threads when dependencies hung, eventually returning HTTP 200 with empty results.^7 This connects an implementation shortcut to recurring failure cost.
- **Dedup is a recurring bug family:** commits separately deduplicated add objects, added-item writes, search results, and display (`f333888e`, `36b0b29d`, `b1efa601`, `336a2bec`, `3e4b3426`). Issue #948 says conflict-aware update was absent; issue #2141 reports production replay duplication despite this history.^2,5 The abstraction never became an end-to-end idempotency contract.
- **Raw versus derived retrieval changed:** history first adopted raw text for knowledge base and later explicitly recalled original text rather than generated memory (`51a782b7`, `f690dad1`). That implies summaries were insufficient as the only caller-facing evidence.
- **Asynchrony failure policy was rewritten:** `d4a1c4fa` preserves fast memories when async fine extraction fails, and a regression test locks it (`tests/mem_scheduler/test_mem_read_handler_fast_cleanup.py:71-102`). This is deliberate backwards/availability behavior, not a semantic claim that fast memories are correct.
- **Backward compatibility became its own abstraction:** API request models normalize deprecated `mem_cube_id`, `moscube`, operation, content, path, and source fields (`src/memos/api/product_models.py:191-231`, `src/memos/api/product_models.py:727-824`); history explicitly consolidated compatibility into models (`1519e33c`). This reveals the original API vocabulary stopped scaling, while handlers still carry legacy-shaped lists (`src/memos/mem_scheduler/task_schedule_modules/handlers/mem_read_handler.py:327-389`).
- **Source ownership was repaired late:** preference extraction gained polluted-source filtering in September 2026 (`9160632f`) and has direct tests (`tests/mem_reader/test_source_filter.py:51-145`). The abstraction’s late arrival implies role/source contamination had escaped the original reader design.
- **Embedding identity was added after breakage:** issue #1333 described silent mixed-space vector failure; commit `a612fe99` implemented re-embedding support.^1 This is direct evidence that storing dimensions alone was not sufficient schema identity.
- **Scale forced indexing/capping:** issue/PR #2077 fixed gateway CPU at 100% from synchronous full-table vector scans (`59c14746`); later `idx_traces_ts` was added specifically to unblock the event loop (`f0f35f`). Defaults that are acceptable locally stopped working under accumulated history.

Admitted shortcuts/incomplete work include: only the first accessible cube is selected in several `MOSCore` operations (`src/memos/mem_os/core.py:724`, `src/memos/mem_os/core.py:950-1083`); tool-memory search is not supported by `SingleCube` (`src/memos/multi_mem_cube/single_cube.py:282`); tree relation reasoning lacks time-sequence recall and summarized nodes omit user/session IDs (`src/memos/memories/textual/tree_text_memory/organize/relation_reason_detector.py:162-194`); working-memory IDs collide with item IDs so one add path is disabled (`src/memos/memories/textual/tree_text_memory/organize/manager.py:239-326`); and some API memory types log “not implemented” (`src/memos/api/handlers/memory_handler.py:84-88`). These are incomplete work, not deliberate answers.

## 4. Unexamined defaults

- **All roles are storable.** There is no retention-policy hook between the TypeScript role union and chunk insert (`packages/memos-core/src/types.ts:3-13`, `packages/memos-core/src/ingest/worker.ts:129-299`). Alternative not represented: user-only, owner-classified, or ephemeral non-user roles.
- **A summary is a single string.** No typed claim, polarity, subject, tier, confidence evidence set, or validity interval appears in `Chunk` (`packages/memos-core/src/types.ts:19-40`). Alternative not represented: structured propositions with independent epistemic metadata.
- **Similarity is cosine over one current embedding space.** Vectors store dimensions but no provider/model/version (`packages/memos-core/src/storage/sqlite.ts:70-75`). Alternative not originally represented: embedding-space ID and dual-index migration; issue #1333 exposed the omission.^1
- **FTS uses trigram tokenization everywhere.** The schema migrates FTS tables to `tokenize='trigram'` (`packages/memos-core/src/storage/sqlite.ts:45-51`, `packages/memos-core/src/storage/sqlite.ts:405-466`). Alternative not represented: language-aware tokenizers or per-language indexes.
- **Recency applies uniformly.** The decay function receives no memory kind/tier (`packages/memos-core/src/recall/recency.ts:12-25`). Alternative not represented: immutable stated facts, expiring observations, and time-anchored episodes with different time semantics.
- **Dedup is scoped by owner and content similarity, not provenance event identity.** Candidate filtering takes optional owner IDs; the public event has no event ID (`packages/memos-core/src/ingest/dedup.ts:12-18`; `packages/memos-schema/src/index.ts:30-42`). Alternative not represented: caller idempotency key plus separately counted semantic recurrence.
- **Missing environment variables become empty strings.** `${NAME}` substitution silently inserts `""` (`packages/memos-core/src/config.ts:4-8`). Alternative not represented: startup validation/failure or unresolved placeholder preservation.
- **Migration errors can be swallowed as “table may not exist.”** Multiple startup migrations use empty catches (`packages/memos-core/src/storage/sqlite.ts:130-214`). Alternative not represented: schema version table and transactional migration failure.
- **Retrieval has a winner.** Relative thresholding derives admissibility from the top candidate (`packages/memos-core/src/recall/engine.ts:169-176`). Alternative not represented: calibrated absolute abstention where all candidates may be bad.
- **Deletion means removal, not suppression.** Python offers delete-by-ID/filter/file paths (`src/memos/api/handlers/memory_handler.py:398-462`), but no tombstone that blocks re-extraction. Alternative not represented: user-authored suppression rule, which Kivi explicitly requires (`../kivi-semantic-memory-position.md:241-248`).
- **Permissions are storage/read isolation, not disclosure semantics.** TypeScript isolation modes decide namespace readability (`packages/memos-schema/src/index.ts:13-25`), while Kivi’s permission dial decides which epistemic tiers may be spoken (`../kivi-semantic-memory-position.md:131-179`). The alternative was not faced in MemOS’s core schema.

## 5. Questions this repo never faced

These arise specifically from Kivi’s position and are absent as enforceable concepts in the audited MemOS schemas.

1. **Who is the subject of a candidate memory, and how is “the user” distinguished from a person mentioned in the user’s text before persistence?** MemOS records actor role/owner, not proposition subject (`packages/memos-core/src/types.ts:19-40`); Kivi prohibits retention of others (`../kivi-semantic-memory-position.md:21-25`).
2. **Which sensitive category classifier is authoritative, what evidence/reason must it emit, and does classifier failure block the write?** MemOS has preference-source filtering but no global hard exclusion gate (`src/memos/mem_reader/source_filter.py:122-183`); Kivi explicitly requires one before storage (`../kivi-semantic-memory-position.md:47-51`).
3. **Can the system retain a source pointer without retaining third-party source content, and how is later provenance display resolved if the source is deleted?** MemOS generally stores raw content beside summaries (`packages/memos-core/src/storage/sqlite.ts:23-34`).
4. **How are `type` and epistemic `tier` made independent in schema, indexing, query authorization, and UI?** MemOS’s type taxonomies do not encode `stated|observed|hypothesised` (`src/memos/api/handlers/memory_handler.py:222-291`; `packages/memos-core/src/types.ts:17-58`).
5. **What constitutes explicit confirmation, and how is it distinguished from the user merely repeating a fact?** MemOS uses repetition for dedup/merge, not tier promotion (`packages/memos-core/src/ingest/worker.ts:168-258`); Kivi forbids self-promotion (`../kivi-semantic-memory-position.md:95`).
6. **How is a hypothesis stored grammatically and technically so it cannot be consumed as a fact?** MemOS has no question-valued belief type; Kivi requires hypotheses to be questions (`../kivi-semantic-memory-position.md:89-94`).
7. **Is disclosure authorization evaluated at retrieval, rerank, prompt assembly, or response generation—and can withheld memories influence any downstream score or model state?** MemOS exposes one ranked list and one injection section (`packages/memos-schema/src/index.ts:80-97`); Kivi separates knowing from saying (`../kivi-semantic-memory-position.md:21`).
8. **How is the dictation path structurally prevented from loading observations/hypotheses rather than merely filtering them?** MemOS uses optional filters/modes, not physically separate accessible tables (`packages/memos-schema/src/index.ts:46-55`); Kivi requires structural non-access (`../kivi-semantic-memory-position.md:181-199`).
9. **What exactly does “That’s not me anymore” suppress: a normalized proposition, an extractor pattern, a source span, an entity/relation, or a semantic neighborhood?** MemOS deletion has no anti-regrowth artifact (`src/memos/api/handlers/memory_handler.py:398-462`); Kivi requires suppression (`../kivi-semantic-memory-position.md:241-248`).
10. **Can a correction change content without falsely rewriting the historical source, and how are corrected belief, original claim, and user correction separately attributed?** MemOS merge history is JSON text and LLM-generated summaries (`packages/memos-core/src/types.ts:35-37`; `packages/memos-core/src/ingest/worker.ts:217-253`).
11. **Do observations decay by wall time, opportunity to observe, number of contrary episodes, or domain-specific cadence?** MemOS applies one global half-life (`packages/memos-core/src/recall/recency.ts:12-25`); Kivi only says observations decay (`../kivi-semantic-memory-position.md:239`).
12. **What is the confirmation budget and interruption policy for asking users to promote observations/hypotheses?** Kivi leaves this open (`../kivi-semantic-memory-position.md:267-275`); MemOS has no corresponding interaction.
13. **How does an abstention prove what was searched and why evidence was insufficient without leaking withheld/sensitive content?** MemOS can note repeated zero-result queries but does not expose a disclosure trace (`packages/memos-core/src/recall/engine.ts:264-294`); Kivi requires an abstention trace (`../kivi-semantic-memory-position.md:227-230`).
14. **What is the durable identity of a belief assembled across multiple transcripts?** MemOS chunks are source-turn oriented and merges retire records; Kivi explicitly requires distributed evidence (`packages/memos-core/src/types.ts:19-40`; `../kivi-semantic-memory-position.md:283`).

## 6. What the tests do not cover

The following decisions could change while the reviewed suite would still largely pass; therefore the repo offers precedent, not evidence.

- **Sensitive and third-party non-retention.** Preference tests distinguish assistant/tool pollution, but no test asserts a global write-path exclusion across entity, episode, and general memory (`tests/mem_reader/test_source_filter.py:51-145`).
- **Kivi-style tier semantics.** No test can distinguish stated, observed, and hypothesised because those fields/states do not exist in the audited models (`packages/memos-core/src/types.ts:19-40`; `src/memos/api/handlers/memory_handler.py:222-291`).
- **Explicit-confirmation-only promotion.** Scheduler version tests exercise increment/persistence, not epistemic promotion (`tests/mem_scheduler/test_version_control.py:51-250`).
- **Correction that blocks re-derivation.** Delete tests check request modes and calls, not reprocessing the same source after deletion (`tests/api/test_memory_handler_delete.py:14-145`).
- **Contradiction versus elaboration under realistic language.** Tree-manager tests use mocked merge outcomes; they do not demonstrate that an LLM judge reliably distinguishes conflicts (`tests/memories/textual/test_tree_manager.py:79-103`).
- **Calibration of `0.80`, `0.65`, `0.45`, MMR `0.7`, or 14 days.** No colocated TypeScript tests or evaluation provenance ties these values to a corpus (`packages/memos-core/src/types.ts:331-363`; `packages/memos-core/src/ingest/task-processor.ts:204-216`).
- **Combined hybrid-ranking quality.** Python retriever tests verify merging/dedup mechanics with mocks, not ranking correctness against relevance judgments (`tests/memories/textual/test_tree_retriever.py:45-160`).
- **All-bad candidate abstention.** The relative threshold formula could admit a weak best result without failing the interaction/mocking tests (`packages/memos-core/src/recall/engine.ts:169-190`).
- **Embedding-model change before issue-driven repair.** The original schema tests did not distinguish model identity because the row lacked it (`packages/memos-core/src/storage/sqlite.ts:70-75`); issue #1333 supplied production-style evidence instead.^1
- **Retry/replay idempotency at the public API.** Basic add tests assert delegation/storage, not repeated delivery with the same event identity (`tests/mem_os/test_memos_core.py:463-530`). Issue #2141 demonstrates the gap.^5
- **Late or out-of-order messages.** Tests exercise sequence fields and queue grouping, not clock skew, replay across sessions, or concurrent contradiction (`tests/mem_scheduler/test_dispatcher.py:199-242`).
- **Disclosure independent of retrieval.** Prompt-building tests check that memories are inserted into templates, not that retrieved memories can be withheld by permission with recorded reasons (`tests/mem_os/test_memos_core.py:689-741`).
- **Provenance after merge/correction/deletion.** Tests verify source propagation and IDs, not that every derived belief remains traceable through multiple merges (`tests/mem_reader/test_project_id_propagation.py:91-346`).
- **Semantic behavior under dependency failure.** There are targeted fallbacks, but issue #1273 shows a caught infrastructure failure could return HTTP 200 with empty recall.^7 A different fail-open/fail-closed answer can pass unit mocks.
- **Cross-session action safety.** Search accepts session fields and prompt injection is integration-specific; issue #1532, not the suite, identified the behavioral hazard.^3
- **Cost/latency budgets.** The suite does not distinguish six versus ten recalled items by total prompt cost; issue #1514 quantified the consequence after deployment.^6
