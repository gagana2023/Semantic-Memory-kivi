# Inverting *Git Context Controller* for Kivi

**Paper:** Junde Wu et al., “Git Context Controller: Manage the Context of Agents by Agentic Git,” arXiv:2508.00031v3, 24 July 2026.  
**Setting used for comparison:** *The Things Kivi Comes to Know* (the attached semantic-memory position).  
**Method:** This is a decision map, not an architecture recommendation. “Underspecified” means the paper does not provide enough information to infer the choice safely. Page links point to the relevant passage in the paper PDF.

## Reading frame

GCC and Kivi overlap at the level of durable, attributable, revisable context, but their objects and failure costs differ. GCC remembers an agent’s project state and reasoning so an autonomous worker can continue. Kivi remembers work-level facts and patterns about a person so the person need not repeat them. GCC’s main failure is task failure or wasted computation; Kivi additionally faces privacy harm, unwanted characterization, disclosure harm, and loss of user agency. Consequently, a precedent from GCC is evidence about long-horizon task performance only where explicitly evaluated—not evidence about safe personal semantic memory.

## 2. Forced choices

These are load-bearing in the paper: changing them would alter what GCC is, remove a component associated with a material performance change, or invalidate the claimed advantage.

| Decision | Why load-bearing in GCC | What the evidence actually isolates |
|---|---|---|
| **D1 — versioned, layered durable state rather than one active stream** | It is the paper’s central intervention and the basis for cross-session navigation. | The full GCC bundle beats controlled long-context, summary, and folding agents on end-task Pass@1. It does not isolate “Git” from “more persistent information plus more calls.” |
| **D3 — agent-chosen milestone commits** | `COMMIT` converts transient traces into the persistent units on which summaries, branches, retrieval, and rollback depend. | Roadmap + COMMIT moves SWE-Bench Verified from 67.2 to 69.1 in the cumulative ablation. COMMIT is not ablated separately from RoadMap. |
| **D7 — isolated branches for divergent reasoning** | Branches instantiate the paper’s multi-trajectory claim and supply the inputs to merge. | Adding BRANCH & MERGE to the preceding cumulative bundle moves 77.8 to 80.2. Branching is not separated from merging. |
| **D8 — synthesis on merge** | Without synthesis, GCC would preserve alternatives but not consolidate them into the canonical roadmap/memory. | Same 77.8→80.2 bundle result. The study does not compare synthesis policies or conflict preservation. |
| **D9 — explicit context retrieval** | Retrieval is what makes externalized detail available again after it leaves the active window. | “Detailed Logs + CONTEXT” enters as a bundle, alongside the already-present Roadmap + COMMIT, moving 69.1 to 75.3. Logs and retrieval are not separately identified. |
| **D10 — hierarchical, bounded coarse-to-fine retrieval** | It operationalizes navigability without loading the full history. The experiments use `K=1`. | The paper compares the full retrieval arrangement to systems with other context strategies, but does not vary hierarchy, `K`, ranking, or semantic versus chronological retrieval. |

Two choices are architecturally important for Kivi but **not empirically load-bearing in this paper**: detailed metadata (D12) appears in a cumulative 75.3→77.8 gain, but its contents/update policy are not isolated; full trace retention (D4/D11) is bundled with retrieval and is never compared with selective evidence retention.

## 3. Unexamined defaults

| Unexamined default | Evidence it is treated as a default | Alternative this line of work rarely tests |
|---|---|---|
| **More retention is safer than forgetting.** Old detail remains externally stored even when absent from the active window. | `log.md` records every OTA cycle; retrieval windows bound exposure, not retention (§2.1–2.2). | Deliberate non-retention: prove usefulness under a storage budget that deletes raw traces and keeps only minimally sufficient, consent-compatible evidence. |
| **The agent may administer its own memory.** The same model doing the task decides when to commit, branch, retrieve, and update plans. | Commands are put in the system prompt and autonomously invoked (§2.2). | Separate memory-policy authority whose decisions the task agent cannot override, with independent evaluation of missed/unsafe writes. |
| **One canonical synthesized account is desirable.** Merge produces a unified summary and updates the global roadmap. | MERGE definition (§2.2). | Preserve irreducible disagreement as first-class state and require later evidence—not generation—to resolve it. |
| **Internal reasoning is legitimate durable data.** OTA “thoughts” are logged and treated as inspectable memory. | `log.md` definition (§2.1). | Store only observations, actions, outcomes, and source evidence; treat generated rationales as ephemeral because they are neither ground truth nor necessary provenance. |
| **Project boundaries are the natural memory boundaries.** A `.GCC/` workspace and shared roadmap define scope. | Filesystem layout (§2.1). | Subject-, relationship-, or purpose-bounded memory where the same event has different retention/disclosure rights depending on whom it concerns and why it was collected. |
| **Chronology plus hierarchy is an adequate retrieval index.** Branch, commit, log window, and metadata segment are the exposed selectors. | CONTEXT options (§2.2). | Claim/evidence retrieval ranked jointly by semantic relevance, freshness, epistemic tier, subject, and permission—with contradictions returned together. |
| **A fluent summary can serve as state.** Previous summary plus new contribution becomes the next coarse summary. | COMMIT formulation (§2.2). | Typed propositions with explicit evidence and uncertainty, where prose is rendered from state but never becomes authoritative state itself. |
| **Rollback is the relevant correction primitive.** Version control supplies reversibility. | COMMIT/BRANCH descriptions emphasize rollback and reversibility. | Forward correction at claim granularity: supersede, demote, suppress re-derivation, and retain a contestable audit trail without restoring an old global state. |
| **End-task correctness is an adequate proxy for memory quality.** | Pass@1 dominates §4; memory-specific failure measures are absent. | Evaluate memory behavior directly, including unauthorized retention, provenance fidelity, stale-belief use, contradiction preservation, abstention calibration, and correction persistence. |
| **The benchmark owner has authority over all retained context.** | No subject, consent, or data-rights model appears despite total trace persistence. | Treat every candidate memory as having a subject, source, purpose, allowed uses, and deletion rights before it can be stored. |

## 4. Questions the paper never faced

These questions come from Kivi’s stated product position, users, and failure modes—not from gaps filled with generic memory-system concerns.

1. **When an interaction contains the user’s words, application context, and another person’s words, what should determine which subject owns each candidate memory and whether it may cross the write barrier?**
2. **When a useful work fact is derived from third-party personal content, what transformation is sufficient to retain work-level residue without retaining or making inferential use of the personal source?**
3. **When a candidate falls near a hard excluded category—work availability versus health, project budget versus personal finances—what should determine whether it is dropped, generalized, or held for confirmation?**
4. **When the same stored item is relevant to both regular dictation and Hey Kivi, what should determine which fields or tiers each surface can structurally access?**
5. **When Kivi retrieves a memory but permission does not allow disclosure, what trace should remain visible without leaking the withheld content?**
6. **When an observed behavioral pattern has many examples but no explicit confirmation, what should determine whether it may influence output, be surfaced as an observation, or remain unused?**
7. **When the user’s request appears to invite deeper inference, what linguistic or interaction event is sufficient to grant one-request hypothesis permission without silently changing the persistent mode?**
8. **When evidence supports a pattern but also admits sensitive explanations, what should determine whether Kivi may store the pattern independently of any explanation?**
9. **When a new statement contradicts an old memory, what should determine whether this is correction, genuine change over time, context-specific variation, identity collision, or unresolved conflict?**
10. **When the user says “That’s not me anymore” or “Forget this,” what representation should prevent the same conclusion from regrowing from retained source transcripts while avoiding a permanent hidden profile of rejected traits?**
11. **When a stated memory is old and unrepeated, what should determine whether it remains authoritative, requires re-confirmation, or becomes historical?**
12. **When an observation decays, what should happen to its evidence, its visibility, and its ability to be re-derived?**
13. **When a hypothesis is unanswered, what event or time boundary should expire it, and what evidence—if any—may survive expiry?**
14. **When Kivi lacks an answer, what should determine the boundary between a useful near-match explanation and an answer-shaped insinuation?**
15. **When confirming uncertain memory would help but interrupt the user, what should determine which candidate consumes the limited weekly confirmation budget?**
16. **When a user edits a memory, what should happen to its epistemic tier and provenance: does the edit become a new stated source, modify the old claim, or coexist with the source it corrects?**
17. **When multiple memories could shape a response, what should determine which were merely retrieved, which were actually used, and which must be exposed in the Why panel?**
18. **When showing source transcripts would reveal third-party material that was correctly not retained as memory, what redaction or evidence representation preserves attribution without violating non-retention?**
19. **When lexical/entity memory improves transcription, what should prevent a contextual fact from changing the user’s dictated meaning rather than merely spelling or formatting it accurately?**
20. **When Kivi is wrong in a low-visibility way—silently applying an observed preference, using a stale employer, or omitting a withheld observation—what signal should make the error detectable to the user?**
21. **When the user removes a memory, what should determine deletion of the derived claim, its provenance, extraction logs, suppression record, backups, and downstream cached outputs?**
22. **When demonstrating that excluded or third-party content was dropped, what audit artifact proves enforcement without itself becoming a retained copy or revealing the prohibited content?**

The attachment leaves several parameters open rather than answering them: extraction timing, decay windows, confirmation budget, evidence thresholds, retrieval mechanics, and cost/latency targets. Those remain real decisions, but the present Kivi description does not establish which way its setting pushes.

## 5. Evaluation gap

### What the paper measured

- **BrowseComp-Plus:** Pass@1 and average tool calls on 150 tasks, across six model backends.
- **SWE-Bench Verified:** Pass@1 and average tool calls on 500 tasks, across the same backends.
- **SWE-Bench Lite:** percent resolved on 300 tasks; for some systems, average dollar cost, tokens, and correct line/function/file localization.
- **Cumulative component ablation on SWE-Bench Verified:** raw Claude 4 Sonnet (67.2), +RoadMap and COMMIT (69.1), +Detailed Logs and CONTEXT (75.3), +Metadata (77.8), +BRANCH and MERGE (80.2).
- **Behavioral counts by difficulty/inference progress:** context calls, active branches, context length, and roadmap updates.

Sources: [§3–4, pp. 5–8](https://arxiv.org/pdf/2508.00031#page=5), especially [Table 1, p. 6](https://arxiv.org/pdf/2508.00031#page=6), [Table 2, p. 7](https://arxiv.org/pdf/2508.00031#page=7), and [Table 3, p. 8](https://arxiv.org/pdf/2508.00031#page=8).

### What evidence the paper does and does not give Kivi

The experiments support a narrow proposition: on the tested autonomous coding and web-research tasks, the full GCC protocol is associated with better end-task success than the selected long-context, summary, and folding baselines, across several model backends. The cumulative ablation further suggests that access to detailed history, explicit retrieval, metadata, and branch/merge operations add value as bundles.

They do **not** establish which personal semantic memories should be written, how beliefs should be typed, how third-party data should be excluded, how contradictions should be represented, how permission should gate disclosure, how correction should prevent re-derivation, or how memory should decay. For those decisions, GCC is a precedent—sometimes a useful contrasting one—but provides no discriminating evidence.
