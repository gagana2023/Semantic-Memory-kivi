# Reflexion: Decision-Space Inversion

This report inverts *Reflexion: Language Agents with Verbal Reinforcement Learning* (Shinn et al., arXiv:2303.11366v4). It maps questions the authors had to answer; it does not recommend answers.

## Scope limitation

The referenced description of the system being built was not present in the accessible conversation workspace. Accordingly, the build-fit column is marked **underspecified** throughout, and §4 cannot be derived from actual users, constraints, or failure modes. Filling those fields without the attachment would manufacture requirements.

## 1. Decision inventory

“Alternatives” includes both explicit contrasts and plausible options the paper did not test. “Load-bearing” means the answer plausibly changes the reported result materially; these choices are collected again in §2.

| ID | Decision question | Paper's answer | Alternatives rejected or not considered | Setting assumptions | Fit for the system being built | Evidence |
|---|---|---|---|---|---|---|
| D01 ★ | When an agent should improve from trial-and-error, what part of the system should change? | Keep model weights fixed; change the actor's prompt context by adding verbal reflections to memory. | Gradient-based policy/value learning; fine-tuning; prompt optimization without episodic memory; external rule updates; tool-policy updates. Traditional RL is explicitly contrasted, but most hybrids are not tested. | Large-model fine-tuning is too costly or slow; in-context adaptation is affordable; task learning fits in context; improvement is needed over a handful of trials. | **Underspecified.** Need model ownership, inference/fine-tuning budget, number of repeated attempts, and persistence horizon. | [§1, pp. 1–2](https://arxiv.org/pdf/2303.11366#page=2); [§3, pp. 3–4](https://arxiv.org/pdf/2303.11366#page=4) |
| D02 ★ | When a trial produces only sparse success/failure evidence, what should carry credit assignment into the next trial? | An LLM-generated natural-language reflection that identifies likely mistakes and proposes a better action or plan. | Preserve scalar reward only; retain raw trajectory; learn a value function; human critique; structured error labels; causal trace analysis. | The reflection model can infer causes from one trajectory and sparse feedback; mistakes are linguistically expressible; actionable prose changes the actor's behavior. | **Underspecified.** Need feedback richness, causal observability, and cost of acting on a wrong diagnosis. | [§1, p. 2](https://arxiv.org/pdf/2303.11366#page=2); [§3 “Self-reflection,” p. 4](https://arxiv.org/pdf/2303.11366#page=4) |

| D06 ★ | Who or what should decide whether an attempt succeeded? | Task-dependent evaluators: environment completion/heuristics or LLM classification for ALFWorld, exact match for HotPotQA, and self-generated test execution for code. | Human review; learned reward model; semantic grading; formal verification; hidden reference tests during iteration; multi-evaluator consensus. | A cheap evaluator correlates strongly enough with true task success; its errors are less costly than extra supervision. | **Underspecified.** Need ground-truth availability and false-positive/false-negative costs. | [§3 “Evaluator,” pp. 3–4](https://arxiv.org/pdf/2303.11366#page=4); [§§4.1–4.3](https://arxiv.org/pdf/2303.11366#page=5) |
| D07 ★ | When should the system interrupt an ongoing trajectory and trigger reflection? | In ALFWorld, trigger after the same action/response repeats more than three cycles or after more than 30 actions; also test LLM binary classification. | Reflect every step; only at terminal failure; learned anomaly/stall detector; progress estimator; human interrupt; adaptive budget. | Repetition and trajectory length proxy hallucination/inefficiency; reset is cheap; delayed intervention does not cause real harm. | **Underspecified.** Need action reversibility, latency budget, and cost accumulated before interruption. | [§4.1, p. 5](https://arxiv.org/pdf/2303.11366#page=5) |
| D08 ★ | After failure, should the next attempt continue from the current world state or restart? | Reset the environment and start a new trial after reflection. | Continue in place; checkpoint and branch; roll back only the causal action; ask for intervention; abandon. | Environments are resettable and approximately deterministic; reset cost is low; useful learning transfers to the fresh episode. | **Underspecified.** Need reset availability, side-effect reversibility, and whether users tolerate repeated attempts. | [§4.1, p. 5](https://arxiv.org/pdf/2303.11366#page=5) |
| D09 ★ | What should be retained after a failed attempt? | Store a distilled, first-person verbal reflection; use the within-trial trajectory as short-term memory but do not retain full prior trajectories as long-term memory. | Full traces; structured state/action/error tuples; verified facts only; counterexamples; external evaluator notes; nothing. | Distillation preserves actionable signal and discards mostly noise; the model's summary is more useful than verbatim experience. | **Underspecified.** Need auditability, replay needs, regulatory retention, and the cost of lossy compression. | [§3 “Memory,” pp. 4–5](https://arxiv.org/pdf/2303.11366#page=5); [§4.2 ablation, p. 7](https://arxiv.org/pdf/2303.11366#page=7) |
| D10 ★ | When memory exceeds the context budget, what should be discarded? | Use a sliding window: usually the last 1–3 reflections; specifically three for ALFWorld/HotPotQA and one for programming. | Semantic retrieval; importance scoring; diversity selection; hierarchical summaries; durable database; decay; learned forgetting. | Recency correlates with utility; only a few trials matter; old reflections are safely discarded; context budget is binding. | **Underspecified.** Need learning horizon, recurrence of old failure modes, and context constraints. | [§3 “The Reflexion process,” p. 5](https://arxiv.org/pdf/2303.11366#page=5); [§§4.1–4.3, pp. 5–7](https://arxiv.org/pdf/2303.11366#page=5); [§5, p. 9](https://arxiv.org/pdf/2303.11366#page=9) |
| D11 | When multiple memories are available, what should determine which one is retrieved and its rank? | All items in the bounded recent-memory window are injected; no relevance retrieval or learned ranking is described. | Embedding similarity; task/entity filters; recency × importance; contradiction-aware retrieval; random/diverse recall; user-curated memory. | With only 1–3 same-task reflections, ranking adds little; every retained item is relevant. | **Underspecified.** Need memory volume, task diversity, and retrieval latency. | [§3 “Memory,” pp. 4–5](https://arxiv.org/pdf/2303.11366#page=5); [§5, p. 9](https://arxiv.org/pdf/2303.11366#page=9) |
| D12 ★ | When stored reflections conflict or a later outcome discredits an earlier reflection, what should happen? | **Underspecified.** Reflections are appended and later evicted by recency; no conflict detection, confidence, correction, or provenance rule is given. | Supersede; reconcile; retain both with confidence; verify against evidence; isolate by task; delete poisoned memory. | Either contradictions are rare within a few trials or the LLM can resolve them from context without explicit machinery. | **Underspecified.** Need expected contradiction rate and failure cost from poisoned memory. | [Algorithm 1 and §3 “The Reflexion process,” pp. 4–5](https://arxiv.org/pdf/2303.11366#page=4) |
| D13 | What form should evaluation feedback take before reflection? | Reduce task evaluation to a scalar/binary reward, then combine it with the trajectory and memory in the reflection prompt. | Preserve rich execution traces as evaluator output; categorical error codes; uncertainty distribution; counterfactual feedback; per-step rewards. | Sparse reward plus trajectory is sufficient for the LLM to reconstruct useful detail. | **Underspecified.** Need whether evaluators can expose richer and more reliable diagnostics. | [§3 “Self-reflection” and process, pp. 4–5](https://arxiv.org/pdf/2303.11366#page=4) |
| D14 ★ | For generated code without access to hidden tests, what should determine whether the candidate is revised or returned? | Generate up to six internal tests, filter for syntactic validity via AST construction, execute them, and return early if all pass; otherwise reflect and revise. | Property-based tests; differential testing; static analysis; formal specs; adversarial test generation; human acceptance; always revise a fixed number of times. | Up to six model-generated tests cover salient semantics; syntax-valid tests are meaningful; execution is safe and cheap; passing internal tests predicts hidden-test success. | **Underspecified.** Need code domain, sandboxing, test oracle, and false-accept cost. | [§4.3, pp. 7–8](https://arxiv.org/pdf/2303.11366#page=7); [§8, p. 9](https://arxiv.org/pdf/2303.11366#page=9) |
| D15 | When test evidence is noisy, which evaluator error should the system prefer? | Prefer false negatives over false positives: unnecessary revision may recover, while a false positive prematurely returns incorrect code. | Optimize balanced accuracy; minimize expected cost; abstain on uncertainty; require independent confirmation. | A mistaken revision is recoverable; releasing wrong code is worse than extra trials; trial budget remains. | **Underspecified.** Need asymmetric failure costs and recovery probability. | [§4.3 “Analysis,” p. 8](https://arxiv.org/pdf/2303.11366#page=8) |
| D16 | What should be discarded from self-generated test evidence? | Discard syntactically invalid test statements; beyond that, filtering for semantic validity, redundancy, flakiness, or adversarial quality is **underspecified**. | Semantic consistency checks; deduplication; mutation testing; cross-model validation; confidence weighting. | AST validity is a useful first gate and test generation quality is adequate on selected benchmarks. | **Underspecified.** Need nondeterminism, side effects, concurrency, and test-generation reliability. | [§4.3, p. 7](https://arxiv.org/pdf/2303.11366#page=7); [§5, p. 9](https://arxiv.org/pdf/2303.11366#page=9) |
| D17 ★ | How many retries should be permitted, and what should stop learning? | Stop when the evaluator passes or a task-specific maximum is reached; ALFWorld reports 12 trials; HotPotQA stops after three consecutive failures; code averages up to eight trials in an appendix experiment. Algorithm 1's loop condition is written ambiguously (`not pass or t < max trials`). | Fixed total compute; marginal-improvement threshold; confidence-based stop; user-defined budget; safety stop; best-of-N without learning. | Repeated trials are cheap; benchmark environments are stable; evaluator “pass” is trustworthy; trial counts are enough to expose gains. | **Underspecified.** Need latency, token/call budget, and consequences of repeated actions. | [Algorithm 1, p. 4](https://arxiv.org/pdf/2303.11366#page=4); [§§4.1–4.2, pp. 5–6](https://arxiv.org/pdf/2303.11366#page=5); [Appendix A, p. 12](https://arxiv.org/pdf/2303.11366#page=12) |
| D18 | Should exploration arise from explicit search or from stochastic retries conditioned on reflection? | Use sampled LLM behavior (temperature 0.7 in HotPotQA) and revised prompts; no explicit branching policy, beam, value-guided search, or off-policy exploration. | Beam/tree search; diverse candidate pools; bandits; value-guided exploration; deterministic correction; off-policy replay. | Model sampling plus reflection supplies adequate behavioral diversity; extra branches are not worth their cost. | **Underspecified.** Need branching factor, action cost, and whether diverse exploration is essential. | [§4.2, p. 6](https://arxiv.org/pdf/2303.11366#page=6); [§7, p. 9](https://arxiv.org/pdf/2303.11366#page=9); [Appendix B, pp. 13–14](https://arxiv.org/pdf/2303.11366#page=13) |
| D19 | When answering multi-hop questions, what should be retrieved and how should it be ranked? | ReAct queries a Wikipedia API and uses returned context; the paper gives examples but does not specify the search API's retrieval model, result depth, reranking, deduplication, or provenance selection. | Ground-truth context; dense retrieval; hybrid search; query expansion; reranking; multi-source retrieval; citation-constrained answering. | Wikipedia is an adequate closed corpus; API ranking is usable; retrieval failures can be repaired through later reflection. | **Underspecified.** Need corpus, freshness, access controls, source trust, and provenance requirements. | [§4.2, p. 6](https://arxiv.org/pdf/2303.11366#page=6); [Appendix D, pp. 16–18](https://arxiv.org/pdf/2303.11366#page=16) |
| D20 | What should be exposed to an end user about the learning loop? | **Underspecified.** The experiments expose final benchmark outputs; reflections are described as interpretable/monitorable, but no user interface, review control, uncertainty, provenance, or correction workflow is evaluated. | Show reflections; show evidence only; confidence/abstention; approval gates; editable memory; silent retries; audit log. | The primary consumer is a benchmark evaluator/researcher rather than an end user making a consequential decision. | **Underspecified.** Need actual user roles, comprehension, and control requirements. | [§6, p. 9](https://arxiv.org/pdf/2303.11366#page=9); task outputs in [§4](https://arxiv.org/pdf/2303.11366#page=5) |
| D21 ★ | When the system is wrong but its evaluator says “pass,” what recovery path should exist? | In code, it prematurely returns the invalid submission; elsewhere no post-pass monitoring or correction path is specified. | Abstain; independent verifier; delayed audit; rollback; user report; continuous monitoring; retain provenance and reopen. | Evaluator false positives are infrequent enough for benchmark use; terminal submissions need no lifecycle after scoring. | **Underspecified.** Need observability after deployment, reversibility, and failure severity. | [§4.3 “Analysis,” p. 8](https://arxiv.org/pdf/2303.11366#page=8) |
| D22 | Across tasks or users, what should persist over time? | Reflections are local to repeated attempts on the same task and held in a tiny sliding window; cross-task/user durable learning is not described. | Global memory; user-specific memory; task-class skills; parameter updates; curated shared lessons; no persistence. | Each benchmark item is independent; useful experience is task-specific; avoiding transfer/interference is acceptable. | **Underspecified.** Need tenancy, personalization, privacy, distribution drift, and expected task recurrence. | [§3 “Memory,” pp. 4–5](https://arxiv.org/pdf/2303.11366#page=5); experimental protocols in [§4](https://arxiv.org/pdf/2303.11366#page=5) |
| D23 | When model capability is insufficient for reliable self-correction, should the same architecture still be used? | The architecture is unchanged; Appendix A reports no Reflexion gain with StarChat-beta and concludes self-correction emerges in stronger/larger models. | Route to stronger critic; human escalation; constrain task; structured diagnostics; forego reflection; train a dedicated critic. | A sufficiently capable proprietary model is available and its cost is acceptable. | **Underspecified.** Need the intended model tier, deployment constraints, and escalation options. | [Appendix A, p. 12](https://arxiv.org/pdf/2303.11366#page=12); [§1, p. 2](https://arxiv.org/pdf/2303.11366#page=2) |
| D24 | How should executable outputs be contained before evaluation? | Advise isolated execution environments because generated code is not validated before execution; the actual isolation design is **underspecified**. | Static validation first; capability sandbox; syscall/network restrictions; no execution; human approval; disposable VM/container. | A sandbox is available; benchmark code is low-risk; isolation overhead is tolerable. | **Underspecified.** Need threat model, allowed resources, secrets exposure, and blast radius. | [§8, p. 9](https://arxiv.org/pdf/2303.11366#page=9) |
| D25 | When environmental conditions are nondeterministic or externally coupled, should test-driven self-evaluation remain the feedback mechanism? | The paper identifies generators, impure/API functions, hardware-dependent outputs, and concurrent behavior as limitations; it does not provide an alternative. | Metamorphic/property testing; simulation; recorded traces; contract monitoring; human validation; probabilistic oracles. | Main experiments are deterministic, pure, resettable benchmark tasks. | **Underspecified.** Need data shape, external dependencies, and nondeterminism. | [§5, p. 9](https://arxiv.org/pdf/2303.11366#page=9) |

## 2. Forced choices

These are the choices marked ★ above. The evidence indicates that changing them would alter the mechanism or reported outcomes, not merely the implementation.

| ID | Load-bearing choice | Why it materially bears the result |
|---|---|---|
| D01 | In-context verbal updating instead of weight updates | This defines what “Reflexion” is and determines its few-shot, no-training cost profile. |
| D02 | LLM-generated reflection as the credit-assignment carrier | The framework's claimed semantic-gradient effect depends on the model producing a correct, actionable diagnosis from sparse feedback. |
| D06 | Task-specific evaluator/oracle | The evaluator controls both learning signal and stopping. Its false positives become terminal errors; its false negatives provoke potentially harmful revisions. |
| D07 | Failure/stall trigger | In ALFWorld, reflection only happens when the heuristic or classifier fires; trigger precision/recall changes which trajectories receive intervention. |
| D08 | Reset after reflection | Reported learning curves assume cheap independent retries; continuation in a side-effectful state would produce a different optimization problem. |
| D09 | Distilled reflection rather than raw trajectory as durable memory | The HotPotQA episodic-memory ablation attributes an additional 8-point gain to the reflective pass over retaining the most recent trajectory. |
| D10 | Tiny recency window | It constrains what prior experience can affect the actor and makes the method feasible within the then-current context window. A retrieval system would change both cost and transfer behavior. |
| D12 | No explicit contradiction/poisoned-memory handling | Because memories directly condition the actor, a wrong reflection can systematically steer every subsequent trial; the paper does not isolate this risk. |
| D14 | Self-generated tests as the code oracle | The HumanEval Rust ablation finds neither tests alone nor unguided reflection improves over the 60% baseline; the composite reaches 68%. |
| D17 | Retry/termination policy | Cumulative “solved” rates are functions of the allowed number of attempts. Different budgets can erase or amplify the reported advantage. |
| D21 | Trust evaluator pass as terminal | The authors connect MBPP underperformance to a 16.3% false-positive test rate; termination on a false pass directly converts oracle weakness into wrong output. |

## 3. Unexamined defaults

These are choices treated as natural machinery rather than isolated research questions. “Untried alternative” means untested here and uncommon in the paper's immediate comparison set—not a claim that no publication has ever attempted it.

| Default inherited or taken for granted | Alternative this line of work leaves largely untested | Why it matters | Evidence |
|---|---|---|---|
| Text is the universal interchange format for state, action, critique, and memory. | Typed causal records that separate observation, inference, counterfactual, confidence, and proposed action. | Free-form prose collapses provenance and uncertainty, making later contradiction resolution difficult. | [§3, pp. 3–4](https://arxiv.org/pdf/2303.11366#page=4) |
| The same class of generative model can act, judge, and diagnose itself. | Deliberately heterogeneous failure modes: symbolic verifier, smaller calibrated critic, or human evaluator paired with the actor. | Correlated errors can turn self-consistency into self-confirmation. | [§3, p. 3](https://arxiv.org/pdf/2303.11366#page=4) |
| A first-person reflection is the right rhetorical form for machine memory. | Evidence-addressed memory written as falsifiable claims with source spans and expiry conditions. | “I should…” language may be behaviorally effective while obscuring whether the premise is true. | [§4.2 ablation, p. 7](https://arxiv.org/pdf/2303.11366#page=7) |
| Failed trials deserve reflection; successful trials need no comparable analysis. | Reflect on near-misses, fragile successes, excess cost, and alternative successful strategies. | Binary success can conceal brittle or unsafe paths that should not be reinforced. | [Algorithm 1, p. 4](https://arxiv.org/pdf/2303.11366#page=4) |
| Recent memories are the relevant memories. | Retrieve by causal situation and known preconditions, even if the lesson is old. | Recency and relevance diverge as tasks become long-lived or heterogeneous. | [§3, p. 5](https://arxiv.org/pdf/2303.11366#page=5) |
| Benchmark reset makes attempts comparable and consequences disposable. | Learn in a non-resettable, partially observable environment with compensating actions and irreversible costs. | Many deployed actions cannot be replayed without changing the world. | [§4.1, p. 5](https://arxiv.org/pdf/2303.11366#page=5) |
| A single scalar/binary outcome can be “amplified” into the missing causal explanation. | Preserve evaluator uncertainty and admit that the outcome underdetermines the cause; request new evidence before updating memory. | The reflection can be precise-sounding but causally unsupported. | [§3, pp. 4–5](https://arxiv.org/pdf/2303.11366#page=4) |
| Exact match is an acceptable QA success oracle. | Entailment plus provenance and calibrated partial credit, evaluated independently. | Semantically correct variants can be rejected; unsupported matching strings can be accepted. | [§4.2, p. 6](https://arxiv.org/pdf/2303.11366#page=6) |
| Syntactically valid generated tests are eligible evidence. | Require the test oracle itself to be justified from the specification, with mutation or adversarial adequacy checks. | A plausible but wrong test can manufacture the learning signal. | [§4.3, pp. 7–8](https://arxiv.org/pdf/2303.11366#page=7) |
| Final task accuracy is the dominant objective. | Optimize a vector of correctness, action cost, recovery burden, user trust, and harm under evaluator error. | Two systems with equal accuracy can differ radically in operational risk. | [§4, pp. 5–8](https://arxiv.org/pdf/2303.11366#page=5) |
| More capable LLMs will make the paradigm improve over time. | Treat capability gains as changing both correction ability and the scale/persuasiveness of self-generated errors, then measure the net effect. | Capability is assumed to improve the critic monotonically without testing correlated failure severity. | [§1, p. 2](https://arxiv.org/pdf/2303.11366#page=2); [Appendix A, p. 12](https://arxiv.org/pdf/2303.11366#page=12) |

## 4. Questions the paper never faced

This section cannot be derived from the absent `<what_i_am_building>` attachment. The paper clearly does not face the questions below, but whether *the target system* raises them is **underspecified**. They are therefore a holding inventory, not a claim about the build.

1. When multiple users share an agent, whose failures and reflections may influence whose future behavior?
2. When a memory contains personal, confidential, or regulated data, what determines whether it may be retained, retrieved, shown, corrected, exported, or deleted?
3. When a user disputes a stored reflection, whose account becomes authoritative and how is the dispute preserved?
4. When a task's facts, policies, tools, or permissions change, what invalidates old reflections?
5. When an action has irreversible external effects, what evidence is required before the system may use trial-and-error at all?
6. When the evaluator is uncertain or unavailable, should the system abstain, escalate, continue, or record an unresolved outcome?
7. When retries consume user time or money, whose budget controls the loop and what cost is exposed before another attempt?
8. When a reflection proposes behavior that conflicts with system policy, organizational policy, or a current user instruction, what precedence rule applies?
9. When memories transfer across tasks, what establishes that a prior lesson's preconditions hold in the new context?
10. When feedback is adversarial, manipulated, or prompt-injected, what may enter reflective memory?
11. When users can see reflections, which content is explanation, which is evidence, and which is merely a model-generated hypothesis?
12. When the system causes harm despite an evaluator “pass,” what is the rollback, notification, audit, and remediation path?
13. When several candidate reflections fit the evidence, what preserves plural hypotheses rather than prematurely collapsing to one story?
14. When model or prompt versions change, should old reflections migrate, expire, be replay-tested, or remain bound to the old policy?

## 5. Evaluation gap

### What the paper measured

| Domain | Primary measurements | Additional measurements/ablations |
|---|---|---|
| ALFWorld | Cumulative proportion of 134 environments solved over up to 12 trials; 130/134 solved with the heuristic configuration. | Failure categories labeled as hallucination vs. inefficient planning; heuristic vs. LLM self-evaluation. ([§4.1, pp. 5–6](https://arxiv.org/pdf/2303.11366#page=5)) |
| HotPotQA | Cumulative exact-match success on 100 questions across trials for CoT, ReAct, and ground-truth-context CoT. | Most-recent trajectory (“episodic memory”) versus episodic memory plus reflection; multiple base models in Appendix A. ([§4.2, pp. 6–7](https://arxiv.org/pdf/2303.11366#page=6); [Appendix A, p. 12](https://arxiv.org/pdf/2303.11366#page=12)) |
| Programming | Hidden-test pass@1 on HumanEval, MBPP, translated Rust subsets, and LeetcodeHardGym. | Internal-test TP/FN/FP/TN; ablations for tests and reflection on 50 hard HumanEval Rust problems. ([§4.3, pp. 7–8](https://arxiv.org/pdf/2303.11366#page=7)) |
| WebShop appendix | Cumulative task success on 100 shopping requests over four trials. | Reflexion does not significantly outperform ReAct; authors attribute difficulty to ambiguous search and insufficient exploration. ([Appendix B, pp. 13–14](https://arxiv.org/pdf/2303.11366#page=13)) |

### Decisions the metrics cannot distinguish

| Decisions with observationally equivalent—or unmeasured—answers | Why the reported metrics give no evidence |
|---|---|
| D01: prompt-memory update vs. another compute-matched adaptation method | Baselines do not match total calls, latency, tokens, or evaluator access, and no fine-tuning/hybrid comparison is run. Similar success would not reveal which adaptation substrate is preferable. |
| D03: separated roles vs. a monolithic or heterogeneous architecture | No controlled role-sharing/model-independence experiment measures correlated errors, latency, or cost. |
| D04–D05: input/state representation and exposed reasoning form | Task success does not distinguish whether visible CoT/ReAct is necessary, faithful, private, or safe. Direct-action and structured-state controls are absent. |
| D06, D13, D15: evaluator form and error tradeoff | Programming reports oracle confusion rates, but ALFWorld and HotPotQA do not measure evaluator calibration against independent judgments. Equal task accuracy can hide different false-positive/false-negative profiles. |
| D07: stall threshold | The paper does not sweep the “>3 repeats / >30 actions” thresholds. A stricter or looser trigger might produce the same final solved rate with different cost and harm. |
| D08: reset vs. continue/checkpoint | All evaluated environments follow the selected retry protocol; there is no non-resettable comparison. |
| D09: prose reflection vs. structured or externally written memory | The HotPotQA ablation separates recent raw trajectory from added self-reflection, but not first-person prose from other compressed, verified, or human-authored memories. |
| D10–D12: eviction, retrieval/ranking, and conflict handling | Memory never grows beyond 1–3 same-task items. The experiments cannot reveal long-horizon forgetting, cross-task interference, retrieval quality, or contradiction poisoning. |
| D14/D16: maximum six tests and AST-only filtering | No sweep of suite size or test-quality filters is reported. Hidden-test pass@1 conflates generator quality, test oracle quality, reflection quality, and revision behavior. |
| D17: stopping policy | Cumulative success necessarily increases with retry opportunity; no compute-normalized, latency-normalized, or user-time-normalized comparison separates method quality from budget. Algorithm 1's `or` condition also leaves the formal stop rule ambiguous. |
| D18: implicit stochastic exploration vs. explicit branching | The negative WebShop result suggests exploration sensitivity but does not compare alternative exploration policies. |
| D19: retrieval corpus/ranking | HotPotQA exact match conflates retrieval and reasoning. Ground-truth-context CoT isolates some reasoning, but no retrieval recall, precision, ranking, source quality, or citation accuracy is reported. |
| D20: what users see and control | There are no users, interface study, explanation-faithfulness measure, trust measure, or correction workflow. Any exposure design could score identically. |
| D21: recovery after a false pass | Benchmark scoring detects some false passes after submission but the system has no post-pass recovery phase; rollback time, detection rate, and residual harm are unmeasured. |
| D22: persistence across tasks/users/time | Each item's loop is effectively local. Cross-task transfer, privacy leakage, personalization, staleness, and catastrophic interference cannot affect the reported score. |
| D23: routing/escalation for weak models | Appendix A shows capability dependence but does not compare fallback policies; equal aggregate accuracy could hide very different abstention/escalation behavior. |
| D24–D25: sandboxing and nondeterministic/external systems | Benchmarks mainly use deterministic, isolated environments. Security containment, network/API side effects, flaky outcomes, and hardware dependence are outside the metrics. |

### Bottom line on evidentiary reach

The paper provides evidence that, on short-horizon, resettable benchmark tasks with cheap repeated attempts and usable automated evaluators, adding model-generated verbal reflection to a very small recent-memory buffer can improve cumulative task success. It gives precedent—but little or no comparative evidence—for durable memory design, conflict resolution, retrieval/ranking, user-facing controls, evaluator calibration outside code, cost-normalized performance, post-deployment recovery, multi-user governance, or operation under irreversible effects.
